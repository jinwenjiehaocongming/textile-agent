Agent 面试问题集 — 纺织 B2B 客服系统
=======================================
基于你的项目真实情况，每条问 + 答。刁钻问题标 🔥

====================================
一、项目深挖（100% 会问）
====================================

Q1: 你的 Agent 架构是怎么设计的？
答：5 节点 LangGraph 图。入口 → 查询改写 → 混合检索(10条) → LLM Rerank(取3) → Agent + 工具(ReAct) → 审核 → END。改写节点消解多轮对话指代，检索用 ChromaDB + BM25 + RRF 融合，Rerank 用 LLM 打分去噪，Agent 绑 search_product 工具按需查价格库存，审核是规则+LLM 双层。端到端评估 94% 通过率 4.6/5。

Q2: 为什么用 RRF 而不是直接拼接向量和 BM25 的结果？
答：直接拼接没法去重也没法加权。RRF 用排名倒数相加，天然把两路结果归一化到同一尺度。我设的 0.5/0.5 权重是评估跑出来的——纺织行业术语多(300T、DTY)，BM25 关键词匹配比纯语义更可靠，五五开比默认的七三开 Precision 提了 5%。

Q3: 🔥 你的 Rerank 10 条全打 10 分怎么办？
答：两种情况。一是知识库太小(47 条)，10 条确实都相关——这是好事不是 bug。二是 LLM 偷懒——加 prompt 约束 "如果都相关也请相对排序，必须有 1-2 个低于 7 分的"。生产环境知识库几万条就不会全 10 分了。

Q4: 查询改写节点为什么放在检索前面？不用改不行吗？
答：多轮对话必须改。客户第一轮说 "T400有没有"，第二轮说 "黑色的多少钱"——第二轮直接搜 "黑色的多少钱" 会命中采购指南和行业术语，跟 T400 完全无关。改写后变成 "T400黑色价格"，命中的是产品相关块。单轮对话改不改差异不大，但我统一过了——LLM 多 0.3 秒换不掉链子。

Q5: 🔥 你的产品查询为什么不做 embedding 而是字符串匹配？
答：产品数据是结构化的——名称、颜色、规格、价格、库存。字符串匹配是 100% 精确的，说 T400 就是 T400，不会因为向量相似度把 T400 四面弹排在牛津布前面。向量检索在这里没有优势，反而引入模糊性。产品库应该用 SQL 精确查询，向量是给非结构化文本用的。

Q6: 检索到的知识 chunk 如果有矛盾怎么办？比如两个不同来源说法不一致？
答：当前 47 条知识都是我手动整理的，不存在矛盾。但生产的解法是：Rerank 时会按照用户具体意图给分，更匹配的那条自然排前面。如果真的冲突，LLM 会在 prompt 里告诉用户 "根据资料 A...但资料 B 提到..."，不做武断删除。这是 LLM 天生比规则系统强的地方——它能处理模糊性。

====================================
二、RAG 与检索（高频）
====================================

Q7: 你的知识库怎么切 chunk 的？
答：手动语义分块。每条面料/工艺/检测标准各自一段，用 --- 分隔，标题【】前置，标签 [类别] 存进 metadata。不分父子块——我的数据量小（47 条），每条都是独立完整知识点。评估验证过：手动分块比自动分块 Recall 高了 6%。

Q8: 🔥 知识库从 47 条涨到 50 万条，你的方案还能用吗？
答：不能。手动分块的前提是数据量可控，50 万条必须自动化。方案：切回 RecursiveCharacterTextSplitter + 父子文档，但评估流程不变——不同场景用不同 chunking 策略，靠评估数据决定调谁。另外 50 万条 Rerank 不可能全打分，前面要加一步粗筛（比如先用 BM25 筛到 100 条再 Rerank）。

Q9: embedding 模型选 text-embedding-v4 的依据是什么？
答：中文 RAG 的主流选择，DashScope 提供，有免费额度。试过本地的 paraphrase-multilingual-MiniLM 效果差一截。如果预算允许生产可以用 bge-large-zh-v1.5，中文 MTEB 榜单最高分。

Q10: 🔥 有没有遇到过向量检索和 BM25 检索结果完全不一致的情况？
答：有。"涤塔夫 190T" 这样的精确规格，BM25 可能一条都搜不到（分词把 190T 切成了 190 + T），但向量能把语义相近的 "涤塔夫 规格 170T-400T" 找出来。反过来 "便宜的里料"——向量可能搜出 "涤塔夫价格低廉"（语义近），但 BM25 搜不到（没 "便宜的" 这个词）。两者互补，RRF 就是解决这个的——各搜各的，分数加一起。

====================================
三、Agent 架构与多 Agent（高频）
====================================

Q11: 你用过哪些 Agent 框架？为什么选 LangGraph？
答：LangGraph 的 StateGraph。选它不是因为流行，是因为它的显式状态管理适合客服场景——每个节点读写同一个 TypedDict，调试时能精确看到每一步状态变化。CrewAI/AutoGen 适合轻量级多 Agent，但状态追踪不如 LangGraph 透明。

Q12: 🔥 你的 Agent 触发了工具调用但工具挂了、超时、返回空，怎么处理？
答：当前工具挂了 LangGraph 会报错，生产必须加容错。方案：工具调用加超时(3 秒) + 重试(最多 2 次) + 降级返回("产品查询暂时不可用，请稍后重试")。Agent 收到降级消息后不能直接回答——要用 fallback 话术 "抱歉系统有点忙，您可以留下联系方式我稍后给您查"。如果连续 3 次工具都失败，标记此会话转人工。

Q13: 为什么审核放在最后而不是对话中间？
答：审核只在最终回复做——中间的工具调用(search_product)和工具结果是事实数据，不需要审。审了的代价是：每次调工具都多一次 LLM 调用，延迟翻倍。而且产品数据本身就该是 "可公开的"——价格和库存又不是机密。

Q14: 🔥 用户说 "你上次说的 12.5/米为什么现在变成 13.5 了"，Agent 怎么处理？
答：不会出现——因为价格是工具从产品库实时查的，不靠记忆。如果价格真变了（涨价了），Agent 会说 "目前查询到的最新价格是 ¥13.5/米，可能较之前有调整，建议以当前报价为准"。关键是不能把 "12.5" 存在 prompt 里——每次都实时查，确保准确性。

Q15: 多 Agent 和单 Agent 怎么选？
答：只有一个原则——什么时候一个 prompt 里出现 "既要...又要...但不能..." 的矛盾句式，什么时候拆。我的系统里 Chat Agent 要追求转化率和客户体验，Review Agent 要冷冰冰地卡安全线，两个目标冲突——必须拆。如果是同一目标下的不同能力(查产品 + 查知识)，一个 Agent 绑多个工具就够了。

====================================
四、评估与质量（高频）
====================================

Q16: 你怎么知道你的 Agent 改好了还是改坏了？
答：三套评估。检索评估 50 道题测 Recall/Precision/MRR，端到端评估 20 道题用 LLM 当裁判打分 1-5。每次改 prompt、换模型、调 RRF 权重都跑一遍。数据说话，不靠感觉。

Q17: 🔥 评估标准是怎么定的？LLM 裁判的分数可信吗？
答：有两个校准手段。一是用期望要点做标注——每道题列出了正确答案该包含的关键词，而不是模糊的 "回答好不好"。二是 LLM 裁判对同一道题用不同 prompt 跑 3 次取中位数。学术上这叫 LLM-as-Judge，Google/Anthropic 都在用。承认局限性——人工标注才是黄金标准，但我的数据量(47 条知识)不值得雇人标。

Q18: 🔥 你在评估里发现过什么意外的问题？
答：最意外的是 "面料克重怎么看多少算厚" 这道题——检索命中了品质检验和采购指南，但都不完全匹配，导致 LLM 回答只说了克重概念没给 "200g以上的算厚" 这个具体回答。发现后我在知识库里单加了一条 "面料规格概念" 明确写了厚薄阈值。评估的价值就是让你发现知识盲区。

====================================
五、LLM 与 Prompt 工程
====================================

Q19: 为什么选 deepseek-chat 而不是 GPT-4 或千问？
答：便宜，中文好。¥1/百万 token 输入，一个客服对话 0.001 元不到。千问免费额度用完了，GPT-4 中文没优势还贵 10 倍。deepseek-chat 的 tool calling 稳定，还没遇到过格式解析失败。但它的审核判断不如 GPT-4 细致——这也是一层规则一层 LLM 的原因，用规则兜底。

Q20: 🔥 LLM 不理你的 system prompt 怎么办？
答：有过。有一次 LLM 在羽绒服面料推荐题里主动说 "我帮您看看我们工厂还有什么其他面料"——这在 prompt 里没写，属于幻觉式服务。解法：prompt 里加 "不要推荐知识库中未提到的面料，不知道就说不知道"，同时降低 temperature 到 0.1。低 temperature 对格式稳定性的影响比 prompt 本身更大。

Q21: 🔥 你的 temperature 设多少？为什么？
答：路由/改写/审核 = 0 或 0.1（格式要求严格，不能有创意）。对话 Agent = 0.3（保留一点自然感但不会胡编）。Rerank 评分 = 0（只要数字，不能有波动）。

Q22: prompt 里放了什么？放了检索到的知识，还有什么？
答：System prompt = 你是谁(宏润纺织 AI 客服) + 你的规则(8 条硬约束) + 面料知识参考(检索到的 chunk 拼接)。不放价格——价格是工具实时查的，放 prompt 里可能过期。

====================================
六、系统设计（高级职位必问）
====================================

Q23: 画一下你的系统架构图。
答：[白板上画]
用户 → 企业微信/Web → Nginx 反向代理 → FastAPI
  → LangGraph Agent(5 节点图)
  → 外部：DeepSeek API(LLM) / DashScope API(Embedding)
  → 内部：ChromaDB(向量检索) / MySQL(产品+用户) / Redis(缓存+队列)

Q24: 🔥 1000 人同时用，瓶颈在哪？怎么解决？
答：瓶颈在 LLM API 并发限制，不是自己服务器。解法：一层队列缓冲（用户请求先入 Redis，Agent 异步处理），二层缓存（30 秒内同样的查询直接返回缓存结果），三层降级（高峰期关 Rerank、审核只做规则不减安全）。极端情况下转人工——客服系统转人工是正常的，不是故障。

Q25: 🔥 你的系统怎么部署？成本多少？
答：Demo：阿里云 ECS 2C4G ¥70/月 + DeepSeek API 按量 ¥20-50/月 + DashScope embedding 免费额度。总计 ¥100/月。生产：加 MySQL(¥200/月) + Redis(¥100/月) + 多台 ECS 做负载均衡，约 ¥1000-2000/月。对一家纺织厂来说，省掉半个客服的工资就回本了。

Q26: 怎么处理消息丢失？比如用户发了一条消息但 Agent 没收到。
答：企业微信自带消息确认机制——回调失败会重试 3 次。Agent 处理前先 ACK 消息，处理完再回复。如果 LLM 调超时，返回 "系统处理中请稍后"。如果 Agent 崩了，企业微信会收到错误回调，这时候人工接入。

Q27: 🔥 怎么防止同行恶意攻击？（刷接口、套底价）
答：基础：API 限流(每人每分钟 20 条消息) + 敏感词拦截(成本价/进货价/底价全拦截)。进阶：行为分析——连续问价格不买 + 每次都在变种问法套利润空间 = 标记可疑用户，降级回复 "建议您直接联系我们销售经理获取详细报价"。但说实话——纺织 B2B 同行攻击不是核心威胁，省成本更重要。

====================================
七、业务与场景
====================================

Q28: 为什么不直接给客户报价而是让客服来回答？
答：因为每笔订单不一样。同一个面料 500 米和 10 万米的单价可以差 20-30%。Agent 给的是标准报价 + MOQ，客户有意向转人工再谈折扣。这是 B2B 的通识——价格永远可谈，Agent 不代替销售，是帮助销售过滤。

Q29: 🔥 客户说 "比隔壁贵，不买了"，Agent 怎么回？
答：不能降价。回复应该是 "我们的产品质量和售后服务有保障，您上次买的 P003 使用效果如何？"——转向质量和服务，不卷入价格战。Agent 的底线是不能自主降价，这是只有销售才能做的事。

Q30: 知识库谁来维护？面料新品种怎么更新？
答：Demo 阶段我自己手动写。生产需要一个 CMS 后台——录入新的面料知识 → 自动 embedding → 增量写入 ChromaDB + BM25。不用重建全库。产品更新简单——MySQL INSERT 一行就行，工具是实时查的。

====================================
八、故障与边界
====================================

Q31: 🔥 ChromaDB 挂了，Agent 还能用吗？
答：能用但降级了。知识检索失败 → knowledge_chunks 为空 → Agent 只靠自己的知识 + 产品查询工具。回复质量会下降——可能编参数，但不会完全不响。告警系统会通知运维重建 ChromaDB。产品查询不受影响——那是独立的数据库。

Q32: 🔥 审核 Agent 把正常回复拦掉了怎么办？
答：审核结果先写日志。如果同一用户连续 3 次被拦且 LLM 认为回复正常(规则判定为 unsafe 但 LLM 觉得很合理)，给运维发告警。当前版本不做自动回滚——安全宁可过杀不可漏放。

Q33: Agent 被问到完全不应该回答的问题（政治、色情）怎么办？
答：第一层拦截：规则关键词过滤，命中直接不调 LLM。第二层拦截：审核 Agent 看到这类内容统一返回 "抱歉，我无法回答这个问题。请问有关于面料的其他问题吗？" 不带任何解释——解释就是给对方信号。

====================================
九、开放性问题
====================================

Q34: 如果重新做这个项目，你会改什么？
答：三点。一，知识库从一开始就写 100+ 条，评估数据会更有说服力。二，产品查询直接用 SQL 不写 JSON 遍历——虽然 Demo 快但生产要改。三，早一点做端到端评估——我是先做了检索评估后来才补端到端的，中间浪费了时间调一些对最终效果没影响的东西。

Q35: Agent 领域接下来 2 年会发生什么？
答：三个趋势。一是 Function Calling 会越来越标准化，各个 LLM 厂商的工具调用格式趋同，写一次工具到处用。二是多 Agent 会从 "酷炫" 变 "标配"——不是因为炒作，是因为审核和安全的独立需求确实存在。三是评估会从 "LLM 做裁判" 进化到 "automatic regression testing"——每次改 Agent 自动跑测试套件，像软件工程一样。
