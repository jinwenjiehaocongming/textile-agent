## 〇、全景：一次咨询的生命周期

```
浏览器/终端 输入消息
  │
  ▼
① app.py 收到请求（/chat 或 /chat/stream）
  │
  ▼
② 身份校验 resolve_user_id(X-User-Id)          [app.py:50-54 → src/user_identity.py:25]
  │
  ▼
③ 记忆加载 get_user + load_recent + 偏好        [src/memory.py:262, 65, 183]
  │
  ▼
④ 挂起态守卫：该用户有单在待审批？→ 直接提示     [app.py:159-162]
  │
  ▼
⑤ 组装初始 state → agent_graph.invoke(state, config)
  │   （config.thread_id = user_id，HITL 依赖）
  ▼
⑥ LangGraph 图内执行：
      query_reformulator（改写检索词）
        → context_retriever（混合检索 RAG，闲聊跳过）
        → supervisor（路由：售前/下单/售后）
        → 分支子 Agent ⇄ MCP 工具（ReAct 循环）
        → review（双层安全审核）
        → END
  │
  ▼
⑦ 拿结果 → 返回 reply（/chat）或 SSE 事件（/chat/stream）
  │
  ▼
⑧ 记忆存档 + 异步偏好提取（任务队列提交，不阻塞主线程）  [app.py:188-190]
```

## 一、场景 A：售前询价（"T400 黑色多少钱"）

### Step 0 服务启动（只发生一次）

**`app.py:27-32`**：`init_mcp({...})` 启动 3 个 MCP Server 子进程（product/order/refund），完成 initialize 握手 + tools/list 工具发现（`src/mcp_client.py:43-49 connect_server`）。

**`app.py:35`**：`agent_graph = build_graph()` 编译 LangGraph 主图（`src/agent.py:486-525`），带 `MemorySaver` checkpointer：
- 8 个节点注册（agent.py:489-496）
- 入口 query_reformulator（agent.py:498）
- 条件边 supervisor → 三分支（agent.py:503-507，路由函数 `supervisor_router` agent.py:458-465）
- 售前环路 agent ⇄ tool_executor（agent.py:510-514，`agent_router` agent.py:471-475）
- 三条路都汇到 review → END（agent.py:515-519）
- `checkpointer = MemorySaver()`（agent.py:523-525）——HITL 挂起/恢复的关键依赖

### Step 1 请求进入

**`app.py:150-151`** `POST /chat`，body: `{"message": "T400 黑色多少钱"}`（`ChatRequest` app.py:57-58）。

### Step 2 身份校验

**`app.py:154`** → `_user_id_from_header(request)`（app.py:50-54）→ `resolve_user_id(headers.get("X-User-Id"))`（src/user_identity.py:25-37）：
- 缺省 → `"guest"`（开发期便利）
- 非法（含 `/`、`..`、中文等）→ 抛 `ValueError` → app.py:53-54 转 **HTTP 400**
- 合法 → 原样返回

> 防的是**目录穿越**：user_id 会拼进文件路径 `data/users/<user_id>/`（memory.py:30-31），所以只允许 `[A-Za-z0-9_-]{1,64}`。

### Step 3 记忆加载 + 挂起态守卫

**`app.py:155`** `memory = get_user(user_id)`（src/memory.py:262-265）→ 内部 `sanitize_user_id` 再兜底一次（memory.py:247-259）→ 取/建 `UserMemory`，初始化 `data/users/<id>/chat.db` 两张表（memory.py:38-51）。

**`app.py:156`** `config = thread_config(user_id)`（src/agent.py:481-483）→ `{"configurable": {"thread_id": user_id}}`。

**`app.py:159-162`** 挂起态守卫：
```python
snap = agent_graph.get_state(config)
draft = find_pending_draft(getattr(snap, "interrupts", None)) if snap else None
if draft:
    return {"reply": pending_reply_text(draft), "pending": True, "draft": draft}
```
如果该用户前一单还挂在人工审批，**不再跑图**，直接返回"您的订单已提交人工审批…"（`pending_reply_text`，src/approval.py:61-75）。防止客户重复下单或把挂起状态冲掉。

**`app.py:164-167`** 加载最近 20 条历史 + 偏好：
```python
history = memory.load_recent(20)      # Redis 命中直接回，没有才查 SQLite（memory.py:65-90）
prefs = memory.retrieve_preferences() # 从用户 ChromaDB 集合取偏好文本（memory.py:183-192）
user_context = "；".join(prefs) if prefs else ""
```

### Step 4 组装 state + invoke

**`app.py:169-174`**：
```python
messages = history + [HumanMessage(content=req.message)]
last_type = memory.get_last_query_type()        # 上一轮模式：chat/place_order/after_sales
state = {"messages": messages, "knowledge_chunks": [], "rewrite_query": "",
         "query_type": last_type, "user_id": user_id, "user_context": user_context}
result = agent_graph.invoke(state, config=config)
```
初始 state 就是 `AgentState`（src/agent.py:166-172）：messages / knowledge_chunks / rewrite_query / query_type / user_id / user_context。

### Step 5 LangGraph 图内执行（关键！逐节点）

#### ⑤-a 节点1：query_reformulator 改写检索词 — `src/agent.py:194-221`

1. `app.py:199` `should_skip_retrieval(last_msg)`（agent.py:155-160）：`len<=4` 且命中小白词（你好/谢谢/在吗…）→ 闲聊直接跳过（返回原话，省 embedding/Rerank/LLM 调用）。
2. 非闲聊：取最近 6 条消息做历史摘要（agent.py:204-207），构造改写 prompt（agent.py:178-191：消解指代、补全省略、生成 2-3 个检索短语）。
3. `_safe_llm(cheap_llm, ...)`（agent.py:212-214，实现 src/llm_utils.py:18-45）：重试/兜底。**LLM 挂了就 fallback 用原话检索**（agent.py:214）。
4. 返回 `{"rewrite_query": "原话\n改写后短语"}`（agent.py:219-221）。

> 例："T400 黑色多少钱" → 改写器输出类似 `T400 黑色价格`。`should_skip_retrieval("T400 黑色多少钱")` 返回 False（`len>4` 且不含白名单词），正常检索。

#### ⑤-b 节点2：context_retriever 混合检索 — `src/agent.py:227-241`

```python
results = retriever.retrieve(query, top_k=5, use_rerank=True)   # agent.py:237
chunks = [r["text"] for r in results]                            # agent.py:238
return {"knowledge_chunks": chunks}                              # agent.py:241
```
`retrieve` 内部（src/retrieval.py:177-246）：
1. **向量检索**：ChromaDB `collection.query`，top10（retrieval.py:201-212），distance 转相似度 `1 - dist/2`。
2. **BM25 检索**：自研 bigram 分词（retrieval.py:40-48）+ IDF 打分，top10（retrieval.py:215-222）。
3. **加权 RRF 融合**（retrieval.py:124-143）：两路都命中的文档分数累加，`vec_weight=0.5` 即向量:BM25 = 5:5；取 top_k(5, 10) 上限 10 个候选（retrieval.py:225）。
4. **CrossEncoder Rerank**（retrieval.py:248-257）：`bge-reranker-base` 对 query+候选 batch 打分，重排取 top5。

返回 5 条知识 chunk 放进 state。

#### ⑤-c 节点3：supervisor 意图路由 — `src/agent.py:397-434`

三层判断（**先规则后 LLM，能省则省**）：

- **Layer 0（agent.py:402-407）**：上一条消息是工具结果且含 `ORD-`（订单生成）或 `退款工单` → 订单/退款刚完成，直接切回售前 `query_type="chat"`。
- **Layer 1（agent.py:410-413）**：`_detect_continuation(messages)`（agent.py:360-382）纯规则判断：上轮 AI 在追问/给确认单（"请问…"、"确认单"、"？"）且用户这轮回答很短 → 延续上一轮模式（不调 LLM）。
- **Layer 2（agent.py:416-434）**：新话题 → LLM 分类（SUPERVISOR_PROMPT agent.py:385-394：sales/order/after_sales 三选一），`cheap_llm` 调用，输出非法就默认 sales（agent.py:428-429），LLM 挂了也默认 sales（agent.py:424）。

然后 `supervisor_router`（agent.py:458-465）按 `query_type` 走条件边：
- `chat` → `agent`（售前）
- `place_order` → `order_agent`
- `after_sales` → `after_sales_agent`

> 本例 "T400 黑色多少钱" 是全新询价 → LLM 判 `sales` → 路由到售前 `agent`。

#### ⑤-d 节点4：agent 售前应答（ReAct）— `src/agent.py:270-311`

1. 拼 System prompt（agent.py:278-282）：`SYSTEM_PROMPT`（agent.py:247-267）注入知识 chunks（`{knowledge}`）+ 用户档案（`{user_context}`）+ 展示工具提示（`{RENDER_HINT}`）。
2. **MCP 动态工具发现**（agent.py:284-285）：`mcp.get_tools_for_langchain(["search_product", "query_order_status"])` 只给售前绑查产品 + 查订单两个工具 + 三个 render 展示工具（agent.py:287）。
3. **过滤孤立 ToolMessage**（agent.py:288-302）：LangChain API 不允许 tool 消息前面没有对应 tool_call——先把历史里的 system 消息去掉，再用"pending 计数"保证 tool 消息与 tool_call 配对，避免 API 400。
4. `_safe_llm(llm_with_tools, [system]+safe, fallback=..., stream_tokens=True)`（agent.py:303-305）：
   - LLM 有 `tool_calls`（比如要查价）→ 返回 `{"messages": [...] + [response]}`，`agent_router`（agent.py:471-475）看到最近消息有 tool_calls → 走 `tool_executor`。
   - 没有 → 直接给文本回复 → 走 `review`。
   - `stream_tokens=True` 表示最终回复走真流式（src/llm_utils.py:48-73：`llm.stream()` 逐 chunk 经 ContextVar pusher 推 SSE）。

> 本例：LLM 看到要查价格 → 调 `search_product(query="T400 黑色")`。

#### ⑤-e 节点5：tool_executor 统一工具执行 — `src/agent.py:317-332`

```python
for tc in last_msg.tool_calls:
    if name in RENDER_TOOL_NAMES:        # render_* 是"数据透传协议"，不执行，回空 ToolMessage
        results.append(ToolMessage(content="", tool_call_id=tc["id"]))
        continue
    result = get_mcp().call_tool(name, args)   # → MCP Client → 子进程 JSON-RPC
    results.append(ToolMessage(content=str(result), tool_call_id=tc["id"]))
```
`call_tool`（src/mcp_client.py:161-196）：找到工具 → 检查子进程存活（死了自动重启，mcp_client.py:175-181）→ RLock 串行发送 `tools/call` 请求 → `_recv` 带 30s 超时读响应（mcp_client.py:137-157）→ 提取文本。**（线程安全 + 崩溃自愈）**

子进程 product_server.py 收到请求（product_server.py:189-202）→ `search_product(query)`（product_server.py:25-87）：关键词 LIKE 匹配 + Bigram 回退 + 计分排序，返回多行文本。

工具结果作为 ToolMessage 追加 → 有向边 `tool_executor → agent`（agent.py:514）回到 agent 节点，LLM 基于工具结果组织最终回答（可能再调工具，最多 ReAct 循环，由 agent_router 控制）。

#### ⑤-f 节点6：review 双层安全审核 — `src/agent.py:338-351` → `review_response`（agent.py:121-149）

1. 非 AI 消息直接跳过（agent.py:340-342）。
2. **第一层规则拦截**（agent.py:128-135）：查 `["成本价","进货价","拿货价","底价","利润多少","加我微信"]`；命中但已礼貌拒绝（抱歉/不能/无法提供 + 无报价数字）→ 放行。
3. **第二层 LLM 审查**（agent.py:137-147）：`cheap_llm` 用 REVIEW_PROMPT（agent.py:101-118）判 safe/unsafe，unsafe 给出安全版 rewrite。
4. 拦截 → 用 rewrite 替换最后一条 AI 消息（agent.py:345-349）；放行 → 原样 END。

### Step 6 返回 + 存档

**`app.py:174`** invoke 返回后：
- 无 interrupt → `app.py:184-192`：
  - `memory.save_last_query_type(result.get("query_type"))` 存本轮的对话模式（续轮用）；
  - `memory.save_messages([HumanMessage, 最终AI回复])` 写 Redis 热缓存 + SQLite（memory.py:53-63）；
  - `get_extraction_queue().submit(memory.extract_and_store, ...)`（app.py:189-190）把**偏好提取**丢给有界任务队列后台跑，不阻塞响应（src/task_queue.py:83-102；偏好提取逻辑 memory.py:123-181：LLM 扫对话 → 只记"客户原话明确说过"的长期信息 → 去重后写入用户 ChromaDB）。
- 返回 `{"reply": result["messages"][-1].content}` → 前端展示。

> **注意**：`/chat` 是同步接口；`/chat/stream`（app.py:274-293）把同样流程变成 SSE 事件流（见第四节）。

## 二、场景 B：下单流程 + HITL 审批（⭐面试最亮的点）

### 阶段 1：客户确认下单 → 图挂起

走法：supervisor 判 `place_order` → `order_agent` 节点（agent.py:437-445）→ `order_agent(order_agent_node)`（src/order_agent.py:171-245）：

1. 绑工具：`search_product + create_order + render_*`（order_agent.py:184-186）。
2. 历史消息转成 human/ai 消息列表（order_agent.py:188-193），加 System（ORDER_AGENT_PROMPT order_agent.py:91-122）+ 指令（order_agent.py:199）。
3. **ReAct 循环最多 5 轮**（order_agent.py:203-243）：
   - LLM 没工具调用但**编了订单号**（内容含"订单已生成/订单号：ORD"）→ 强制追加 HumanMessage 纠正，再问一轮（order_agent.py:236-241）——**防幻觉**。
   - LLM 调 `create_order` → 走 `_approve_then_create(args, customer_id)`（order_agent.py:218-222）↓

**`_approve_then_create`（order_agent.py:125-168）——HITL 核心**：
```python
draft = {product_name, product_id, color, quantity, unit_price, total, phone, address, delivery_date}  # order_agent.py:145-155
register_pending(customer_id, customer_id, draft)   # order_agent.py:157 → src/approval.py:22 登记待审批
decision = interrupt({"type": "order_approval", "draft": draft})   # order_agent.py:158 ⛔ 挂起！
remove_pending(customer_id)                         # order_agent.py:159（resume 重放时执行）
approved = bool(decision.get("approved"))
if approved:
    return get_mcp().call_tool("create_order", args)   # order_agent.py:166 审批通过才真正写库
return "订单未通过人工审批，已取消..."                  # order_agent.py:167-168
```

`interrupt()`（langgraph.types）做的事：
- 图执行**在此暂停**，当前 state（含 pending 的工具调用参数）被 **checkpointer 落盘**（thread_id=user_id）。
- invoke 返回 `{"__interrupt__": [Interrupt(value={...draft})]}`。

**返回链路**：app.py:176-182 检测到 `__interrupt__` → `find_pending_draft`（src/approval.py:52-58）→ 返回 `{"reply": pending_reply_text(draft), "pending": True}`，客户看到"📋 您的订单已提交人工审批…"。

> ⚠️ 关键细节：`interrupt()` 挂起时 **create_order 并没有执行**！只有审批通过后（resume 重放）才真正调用工具写库。

### 阶段 2：销售经理审批 → 恢复图 → 写订单

**审批列表**：`GET /approval/pending`（app.py:212-215）→ `list_pending()`（approval.py:32-39），按提交时间排序返回。

**通过**：`POST /approval/approve {"thread_id": "<user_id>"}`（app.py:251-254）→ `_resume_approval`（app.py:223-248）：
```python
config = thread_config(thread_id)                     # thread_id == user_id
result = agent_graph.invoke(Command(resume={"approved": True, "reason": ...}), config=config)  # app.py:232-234
remove_pending(thread_id)                             # app.py:235
```
- `Command(resume=...)` 告诉 LangGraph"从上次 interrupt 的地方继续"，**整个图会重放执行到 interrupt 点**（这就是为什么下单 LLM 必须 temperature=0）。
- 重放后 `interrupt()` 返回 resume 值 → `_approve_then_create` 继续 → `approved=True` → **真正调用 `create_order`** → 子进程 order_server 生成订单号写 orders.db（order_server.py:38-77：`ORD-日期-时分秒微秒+随机4位`，防同秒 UNIQUE 撞车）。
- 返回给客户的文案（✅ 订单已生成！订单号：…）作为最终 AI 消息 → 走 `review` 审核 → END。
- **`app.py:238-246`**：把审批结果 AI 消息存进该用户记忆，客户下次查历史/再对话能看到。

**拒绝**：`POST /approval/reject` → 同样 resume，`approved=False` → 返回"订单未通过人工审批，已取消"（order_agent.py:167-168），不写库。

### 阶段 3：挂起态守卫（防重复下单）

客户在待审批期间再发消息 → app.py:159-162 的守卫直接拦截提示，不跑图。

## 三、场景 C：售后流程（"收到的布有破洞"）

supervisor 判 `after_sales` → `after_sales_agent` 节点（agent.py:448-455）→ `after_sales_node`（src/after_sales_agent.py:106-153）：

1. 绑工具：`query_order + create_refund + render_*`（after_sales_agent.py:111-113）。
2. 拼 System（AFTER_SALES_PROMPT 内嵌退货规则：纬斜>3%、色差超半级、破洞油污超四分制可退；已裁剪/定制色/超30天不可退）。
3. ReAct 循环（after_sales_agent.py:128-151）：
   - 客户没给订单号 → 先 `query_order` 或直接问；
   - 符合退货条件 → 调 `create_refund(order_no, reason)` → refund_server 在 orders.db 的 refunds 表插入"待审核"工单（refund_server.py:38-54）；
   - 调完 create_refund → 直接返回工具结果消息（after_sales_agent.py:147-149），走 review → END。
4. 返回文案含"✅ 退款工单已生成！…"；`after_sales_agent_node`（agent.py:448-455）检测到"退款工单已生成"把 query_type 切回 chat。

## 四、场景 D：SSE 流式路径（/chat/stream）

入口 `app.py:274-293` `chat_stream` → `stream_chat(...)`（src/stream_chat.py:65-207）。

**事件协议**（stream_chat.py:8-13）：
```
{"type":"start"}                            连接就绪
{"type":"node","node","label","detail"}     图节点执行过程（多个）
{"type":"token","content":str}              最终回复 token 流（多个）
{"type":"done","content":str,"data":?...}   最终完整回复（权威）+ 可选表格数据
{"type":"pending","content":str,...}        订单挂起待审批
{"type":"error","content":str}              异常
```

**线程模型**（stream_chat.py:14-21 + 90-165）：
1. `_run_graph`（stream_chat.py:114-122）放**后台线程**：`set_token_pusher(lambda text: emit("token", text))`（ContextVar 注入 token 推送通道，src/token_stream.py:25-27）→ `graph.stream(state, config, stream_mode="updates")` 逐节点产出事件 → `emit("node_event", ev)`。
2. 统一事件管道：`src_queue`（threading.Queue）+ `dst_queue`（asyncio.Queue）+ `_pump` 协程把线程队列搬到 asyncio（stream_chat.py:98-111）——**线程 → asyncio 的桥梁**，`asyncio.to_thread(src_queue.get)` 阻塞等待。
3. 主生成器消费：`token` 直接 yield；`node_event` 里若有 `__interrupt__` → yield `pending` 事件并中断（stream_chat.py:142-156）；否则对每个节点用 `NODE_LABELS` + `describe_node`（src/node_events.py:18-87）生成中文标签（改写查询/知识检索/意图路由/…）yield 出去。
4. 流结束：`__done__` 哨兵退循环（stream_chat.py:133-134）→ `_stop_pump()` 防线程泄漏（stream_chat.py:106-112）→ 从 checkpoint 取最终态（stream_chat.py:167-172）→ 提取 render 表格数据（stream_chat.py:179-183）→ yield `done`。
5. 存档 + 偏好提取（stream_chat.py:190-203）与 /chat 一致。

**token 流怎么通**：`llm_utils._safe_llm(stream_tokens=True)`（src/llm_utils.py:34-35）→ `_invoke_streaming`（llm_utils.py:48-73）：`llm.stream(messages)` 逐 chunk → `pusher(content)`（chunk 内容为空——工具调用轮——天然不推字）→ `acc = chunk if acc is None else acc + chunk`（AIMessageChunk 累加，含 tool_calls）→ 返回累加结果，行为与 invoke 一致；流中途异常回落 `invoke()` 保正确性。

> 为什么之前不做 token 流式？旧网关首包 15-38s，token 流没意义；换官方 DeepSeek API 首包 1-3s 才做（docs/UNDERSTANDING.md:125-126）。**首包延迟决定流式价值**——面试可引。
