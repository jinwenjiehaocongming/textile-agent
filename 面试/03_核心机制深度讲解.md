## 机制 1：LangGraph 图编排（有向图状态机）

### 是什么
用 `StateGraph` 把一次咨询编排成**有向图**：节点（做事的函数）+ 边（流转）+ 条件边（按 state 决定去哪）。这是当今 Agent 编排的主流框架（LangGraph / AutoGen / CrewAI / Dify 等）。

### 代码在哪
- 建图：`src/agent.py:486-525` `build_graph()`
- 状态定义：`src/agent.py:166-172` `AgentState(TypedDict)`：messages / knowledge_chunks / rewrite_query / query_type / user_id / user_context
- 节点：8 个纯函数（agent.py:194/227/270/317/338/397/437/448）
- 路由函数：`supervisor_router`（agent.py:458-465）、`agent_router`（agent.py:471-475）

### 怎么实现的
```python
builder = StateGraph(AgentState)
builder.add_node("query_reformulator", query_reformulator)   # 节点注册
...
builder.set_entry_point("query_reformulator")                 # 入口
builder.add_edge("query_reformulator", "context_retriever")   # 普通边
builder.add_conditional_edges("supervisor", supervisor_router, {  # 条件边
    "agent": "agent", "order_agent": "order_agent", "after_sales_agent": "after_sales_agent"})
builder.add_conditional_edges("agent", agent_router, {"tool_executor": "tool_executor", "review": "review"})
builder.add_edge("tool_executor", "agent")   # 工具循环边：agent ⇄ tool_executor
...
builder.add_edge("review", END)
return builder.compile(checkpointer=MemorySaver())
```

**状态语义**：每个节点函数接收 `state`（整个 AgentState 快照），返回 `dict` 字段就**合并**进 state（字段级更新，不是整体替换）——这是 LangGraph 与手写循环的根本区别：状态显式、可回放、可检查点。

### 为什么这么设计（面试回答要点）
1. **显式编排 vs 隐式 prompt**：多步流程（查价→确认→下单→审核）用图表达，比让 LLM 自己在 1000 字 prompt 里"记住流程"可靠——图是确定性的，LLM 只负责图内的"决策点"和"生成"。
2. **分支/循环**：条件边实现三分支路由和 ReAct 工具循环；手写 `while` 只能做线性流程。
3. **可检查点（checkpoint）**：配合 MemorySaver 实现 HITL interrupt/恢复（机制 5）——这是纯 ReAct 循环做不到的。
4. **可观测**：`graph.stream(stream_mode="updates")` 逐节点看到中间状态（机制 7 的节点事件流就是靠它）。

### 追问
- **StateGraph 和 Graph 区别？** StateGraph 有共享状态自动合并；Graph 是无状态消息流。
- **节点更新 state 是覆盖还是合并？** 按返回的 key 合并（Annotated/reducer 可定制，比如 messages 用 operator.add）。
- **最大循环次数？** LangGraph 默认 recursion_limit（约 25）；本项目 ReAct 在 agent 层还有自己的 5 轮上限（order_agent.py:203）。

## 机制 2：Supervisor 意图路由（状态机 + LLM 分类）

### 是什么
决定当前消息走哪个子 Agent：售前 `chat` / 下单 `place_order` / 售后 `after_sales`。

### 代码在哪
`src/agent.py:397-434`，规则函数 `_detect_continuation`（agent.py:360-382），路由 `supervisor_router`（agent.py:458-465）。

### 怎么实现的 —— 三层漏斗（能省则省）
- **Layer 0 状态复位**（agent.py:402-407）：上一条是工具结果且含 `ORD-` / `退款工单` → 刚完成订单/退款 → 切回 chat，避免"你好"又走下单 Agent。
- **Layer 1 规则延续**（agent.py:360-382 + 410-413）：**不调 LLM**。判断条件（AND）：
  - 历史 ≥2 条；
  - 上一条 AI 在追问（含"请问/提供/？/选哪"）或给确认单（"确认单/请确认"）；
  - 且用户回复很短（<10 字且不含产品词）。
  - 例外：AI 已说"订单已生成/ORD-"则不延续（agent.py:373-374）；闲聊词不延续（agent.py:375-376）。
  - 例：AI 问"请问您的收货地址是？"，用户回"杭州" → 延续下单模式，不调 LLM。
- **Layer 2 LLM 分类**（agent.py:416-434）：新话题才调 `cheap_llm`，prompt 只让输出一个词（sales/order/after_sales，agent.py:385-394）；非法输出 → 默认 sales（agent.py:428-429）；LLM 异常 → 默认 sales（agent.py:424）。**"闲聊永远是 sales，不确定就选 sales"** 是 prompt 里写死的兜底策略。

### 为什么这么设计
- **省成本省延迟**：大部分"延续"场景一个正则就判了，不用花 LLM 调用。
- **稳**：规则是确定的、可单测的（tests/test_supervisor.py 只测规则层，不触发 LLM）；LLM 分类只在这个规则回答不了时兜底，把不确定性控制在最小范围。
- **query_type 持久化**：`save_last_query_type`（memory.py:98-102）把上一轮模式存 SQLite，Web 重启后跨请求延续。

### 追问
- **为什么不直接让 LLM 每轮都分类？** 延迟 + 成本 + 不确定（同一句话可能判来判去）。
- **规则能覆盖所有情况吗？** 不能，所以有 Layer 2。规则追求"高精确不误伤"，LLM 追求"覆盖面"。
- **为什么 Layer 1 判断的用户短回复要排除产品词？** 用户回"T400"可能是在追问产品而不是回答确认单，排除后交给 LLM 判。

## 机制 3：混合检索 RAG（向量 + BM25 + RRF + Rerank）

### 是什么
先用两种召回（语义向量 + 关键词），融合后精排，是当前 RAG 的"标准作业"（Dense + Sparse + Fusion + Rerank）。

### 代码在哪
`src/retrieval.py`：分词 `tokenize`（40-48）、BM25（54-118）、RRF（124-143）、`HybridRetriever.retrieve`（177-246）、`rerank`（248-257）。

### 怎么实现的
1. **分词**（retrieval.py:40-48）：英文/数字整 token + 中文 **bigram**（相邻两字）——无分词器时的轻量中文切词方案（"黑色弹力" → 黑色/色弹/弹力）。
2. **向量召回**（retrieval.py:201-212）：ChromaDB（bge-base-zh-v1.5 embedding）top10，距离转相似度 `1 - dist/2`。
3. **BM25 召回**（retrieval.py:215-222）：自研实现，`score = Σ idf² · tf·(k1+1) / (tf + k1·(1-b+b·len/avgdl))`，k1=1.5 b=0.75（retrieval.py:99-101）。
4. **加权 RRF 融合**（retrieval.py:124-143）：
   ```
   score(text) = Σ_source weight / (k + rank)     k=60
   vec_weight=0.5，bm25_weight=0.5
   ```
   同一文本两路都命中 → 分数累加（retrieval.py:136-140）。RRF 优点是**只看排名不看原始分**，不需要对齐两个异构打分体系（余弦相似度 vs BM25 分数量纲完全不同）。
5. **CrossEncoder Rerank**（retrieval.py:248-257）：对 query×候选拼 pair 喂 `bge-reranker-base`，得相关性分，重排取 top_k。BiEncoder（向量召回）把 query 和 doc 独立编码比较弱；**CrossEncoder 把 query+doc 一起过 Transformer 直接输出相关性**，更准但更慢，所以只对 top10 精排（召回多取、精排后取 5）。

### 为什么这么设计
- 向量擅长语义（"羽绒服用什么面料" ≈ "棉服里料推荐"），但**实体/型号/数字**召回弱（"T400" 这种专名）；BM25 擅长精确词匹配但不懂语义。二者互补，消融评测（scripts/eval_retrieval.py，85 题）验证混合 > 任一单路。
- RRF 解决了「向量分的量纲 ≠ BM25 分的量纲」没法直接相加的问题。
- Rerank 把精度再提一档，且本地模型免费毫秒级。

### 追问
- **为什么 BM25 TF 部分用 idf²？** 检索式里对长查询的常用变体（2 次幂提高"稀有词"权重），本实现与 build_index 保持一致（retrieval.py:101 vs build_index.py:179）。
- **RRF 的 k 为什么取 60？** 经典论文默认值（防止 rank=0 除零 + 调节两路贡献）。
- **Rerank 是 bge-reranker，为什么不用 LLM rerank？** 贵、慢；本地 CrossEncoder 毫秒级。LLM rerank 适合小候选集合的高质量场景。
- **检索不到怎么办？** Agent prompt 写明"不知道就诚实说不知道，不要编"（agent.py:252）。

## 机制 4：MCP 工具层（自研 Client + JSON-RPC over stdio）

### 是什么
MCP（Model Context Protocol，Anthropic 提出）把"工具/数据源"做成**独立进程的协议服务**，Agent 通过协议发现和调用工具，而不是把工具函数硬编码在 agent 代码里。本项目是**自研的轻量 MCP Client**（不依赖 mcp 官方包，纯标准库）。

### 代码在哪
- Client：`src/mcp_client.py`（整个文件 285 行）
- Server 三个：`src/mcp_servers/product_server.py` / `order_server.py` / `refund_server.py`
- 工具发现使用处：`src/agent.py:284-287`、`order_agent.py:184-186`、`after_sales_agent.py:111-113`

### 怎么实现的
**Server 侧**（product_server.py:147-215 main）：
```
for line in sys.stdin:                    # 逐行读请求（JSON-RPC 2.0，一行一个 JSON）
    method = request.get("method")
    if method == "initialize":   回 serverInfo + 协议版本      (product_server.py:163-168)
    elif method == "tools/list":  回工具名 + description + inputSchema  (product_server.py:170-187)
    elif method == "tools/call":  校验参数 → 执行 → 回 content 数组 (product_server.py:189-202)
    # 响应写 stdout，一行 JSON：{"jsonrpc":"2.0","result":...,"id":...}
```

**Client 侧**（mcp_client.py）：
1. `init_mcp({name: [python3, path]})`（mcp_client.py:259-277）：spawn 子进程 → `_handshake`（initialize → initialized 通知 → tools/list，mcp_client.py:61-80）→ 登记工具。
2. `get_tools_for_langchain(names)`（mcp_client.py:216-234）：转成 LangChain `bind_tools` 格式 → `llm.bind_tools(...)` 让 LLM 知道有哪些工具可用。
3. `call_tool(name, args)`（mcp_client.py:161-196）：
   - 子进程死了（poll() 非 None）→ `_restart_server` 自动重启 + 重新握手（mcp_client.py:175-181 / 82-100），这是**崩溃自愈**；
   - `RLock` 串行化请求（mcp_client.py:184）——JSON-RPC 响应不带请求标识，并发时 A 的请求结果可能被 B 收走（**串线**），所以全局锁，同一时刻只有一个 in-flight 请求（工具是毫秒级本地 SQLite，串行代价可忽略）；
   - `_recv`（mcp_client.py:137-157）：读线程 + `join(timeout=30)`，超时抛 ConnectionError——**绝不永久阻塞**（防子进程僵死）；
   - 超时/失败 → 重启 Server 重试一次（mcp_client.py:190-194）。

**工具权限隔离**（重要设计）：
- 售前只挂 `search_product` + `query_order_status`（agent.py:285）
- 下单只挂 `search_product` + `create_order`（order_agent.py:185）
- 售后只挂 `query_order` + `create_refund`（after_sales_agent.py:112）

> 即"最小权限"：售前 Agent 根本看不到 create_order 工具，杜绝"售前会话里 LLM 顺手下了单"。

### 为什么这么设计
- **解耦**：工具变成独立进程，参数校验、驱动的库、错误隔离都在子进程；Server 可以被任何 MCP Client 复用（README 原话：agent.py、order_agent.py、甚至外部系统）。
- **协议化**：agent 代码不 import SQLite、不 import 业务函数，只认"工具名 + JSON Schema"，新增工具=新增 Server，不用改 agent。
- **容错**：子进程崩了不自愈，客服就废了；重启+重试是廉价的高可用。

### 追问
- **为什么不用官方 mcp 包？** 项目早期为了零重依赖/可掌控，纯标准库实现（能讲清楚协议细节反而加分）。
- **同步串行会不会慢？** 本地 SQLite 毫秒级，串行可忽略；真要高并发吞吐换 HTTP 传输（生产演进方向）。
- **JSON-RPC 为什么能"串线"？** 响应里只有 id。其实本项目带了 req_id（mcp_client.py:107-113），串行化后 id 恒等；如果去掉锁用 id 匹配也能并发，但实现复杂，串行最简单可靠。
- **MCP vs Function Calling？** Function calling 是 LLM 侧的调用协议；MCP 是工具服务侧的标准化协议（发现/描述/调用/传输）。两者可结合：MCP 提供工具，bind_tools 转成 function calling schema 给 LLM。

## 机制 5：HITL 人工审批（interrupt + checkpointer + Command resume）⭐

### 是什么
Human-in-the-Loop：AI 生成订单草案后**暂停**，等人类（销售经理）批准才真正执行写入。金融/下单/删除等高风险操作的标准做法。

### 代码在哪
- 挂起：`src/order_agent.py:125-168` `_approve_then_create`（interrupt 在 158 行）
- 注册表：`src/approval.py`（整个文件）
- 编译带 checkpointer：`src/agent.py:521-525`
- 恢复：`app.py:223-248` `_resume_approval`；CLI 版 agent.py:594-609

### 怎么实现的（完整状态机）
```
LLM 调 create_order
  → _approve_then_create: 组装 draft, register_pending (approval.py:22)
  → interrupt({"type":"order_approval","draft":draft})      ⛔ 图挂起, checkpoint 落盘
      ↓ 返回 __interrupt__ → 前端显示"已提交人工审批"
  （人类时间）销售经理看 /approval/pending → 点通过/拒绝
      ↓
  graph.invoke(Command(resume={"approved": True}), config=thread_config(user_id))
      ↓ LangGraph 重放
  interrupt() 返回 resume 值 → approved=True
  → get_mcp().call_tool("create_order", args)   ✅ 这才是真正写库
  → 订单号返回 → 走 review → END
```

**为什么必须要 checkpointer**：interrupt 挂起时，图引擎要把「执行到哪个节点、state 快照、pending 的工具调用」存起来（thread_id 作 key）；恢复时从检查点重放。没有 checkpointer，LangGraph 不知道"挂在哪"，也无法恢复——所以 `compile(checkpointer=MemorySaver())` 是硬前提（agent.py:525）。

**为什么下单 LLM 要 temperature=0**（order_agent.py:39）：resume 时整条路径会**重放**（回到挂起点重跑）。如果 LLM 有随机性，重放时可能不再调 create_order 或改口问别的——温度 0 保证同输入同输出。
> 这是本项目最值得讲的工程细节：**HITL 与"确定性生成"是配套的**。

**为什么要有 approval.py 注册表**：
- `interrupt` 挂起后，系统侧需要一个"面上"的登记，让 /approval/pending 能列出待审批单（approval.py:32-39）；
- 挂起态守卫（app.py:159-162）靠 `find_pending_draft` 判断该用户是否在待审批；
- 线程安全（Lock）+ 进程内 dict，与 MemorySaver 同样"生产换 Redis/DB，接口不变"（approval.py:10-11）。

**为什么审批通过要把结果写回客户记忆**（app.py:238-246）：客户侧看不到审批管理端，得让他下次查历史/再对话时看到"订单已生成"的结果。

### 追问
- **interrupt 与 checkpoint 什么关系？** interrupt 是"挂起点"，checkpoint 是"挂起的记忆"。没 checkpoint，interrupt 无法恢复。（LangGraph 文档原话：interrupt 前必须配置 checkpointer）
- **Resume 语义是"重放"还是"从断点继续"？** 重放：从头执行到断点，再接着走；所以断点之前的节点都要"幂等"（这就是为什么 rewrite/retrieve 是纯函数、注册表 register 幂等覆盖 approval.py:23）。
- **如果审批期间服务重启？** MemorySaver 是进程内，挂起会丢（已知边界，生产换 Postgres）。
- **为什么不用"先写库再人工改"？** 写库即生效，无法回滚或需要补偿逻辑；"先审批后写库"把高风险动作锁在人类手里。
- **怎么防重复下单？** 挂起态守卫（app.py:159-162）：待审批期间用户再发消息直接提示，不跑图。

## 机制 6：三层用户记忆（Redis 热缓存 / SQLite 持久化 / ChromaDB 偏好）

### 是什么
按 user_id 隔离的记忆体系：短期热缓存（快）→ 中期消息存档（全）→ 长期偏好档案（精）。

### 代码在哪
`src/memory.py`：`UserMemory`（27-192）、缓存层（196-241）、`get_user`（262-265）。

### 怎么实现的
**Layer 1 热缓存**（memory.py:196-241）：
- 优先 Redis：`chat:<user_id>` list，`rpush` + `ltrim(-50,-1)` 只留最近 50 条 + `expire 3600s`（memory.py:222-231）；
- Redis 没跑 → 降级进程内 dict `_dict_cache`（memory.py:227-231，同样限 50 条）——**优雅降级，不崩**。
- 读：`_cache_load_recent`（memory.py:215-219），命中直接返回，省 SQLite 查询。

**Layer 2 SQLite 存档**（memory.py:38-102）：
- 每用户一个 `data/users/<id>/chat.db`：conversations（id/role/content/created_at）+ profile（key/value，存 last_query_type）；
- `save_messages` 双写：缓存 + SQLite（memory.py:53-63）；
- `load_recent`：缓存不命中才查 SQLite，并**回写缓存**（memory.py:78-90）。

**Layer 3 偏好档案（ChromaDB + LLM 提取）**（memory.py:123-192）：
- 后台（任务队列）异步跑 `extract_and_store`：LLM 扫最近 10 条对话，只提取"客户**原话明确说过**的长期信息"（身份/联系方式），**严禁**从订单反推、记颜色偏好/预算（memory.py:137-151）——prompt 里刻意收紧，宁可漏记不可错记；
- 提取结果写每用户 ChromaDB collection（memory.py:157-175），写入前做相似度去重（distance<0.15 跳过，memory.py:163-165）；
- 每轮对话启动时 `retrieve_preferences()` 取出（memory.py:183-192），注入 System prompt 的 `{user_context}`（agent.py:280），实现"记得你"。

**为什么三层**：缓存层快但易丢（Redis 过期/内存重启）；SQLite 全但慢；偏好层是"提炼"——给 LLM 的不是 20 条原文而是 3 条结论，省 token 且命中要害。

### 追问
- **为什么偏好提取是异步的？** 主线程已经要返回回复了，提取是尽力而为的后台任务；同步会拖慢响应。
- **为什么不用向量库存全部历史？** 历史是线性时间序列，SQLite 顺序读足够；向量库用于"无结构偏好的语义检索"，各司其职。
- **多用户怎么隔离？** user_id 贯穿：路径 `data/users/<id>/`、Redis key `chat:<id>`、Chroma collection 都是按用户分（memory.py:28-33 + 111-121）；Web 层 X-User-Id 注入 + 校验（user_identity.py）。

## 机制 7：SSE 流式（节点事件 + token 流）

### 是什么
两层流式：**过程层**（图节点实时可见：改写→检索→路由→应答→审核）+ **内容层**（最终回复 token 逐字推送）。

### 代码在哪
- 入口：`app.py:274-293`；封装：`src/stream_chat.py`（整个文件）
- 节点描述：`src/node_events.py`
- token 通道：`src/token_stream.py`
- LLM 流式调用：`src/llm_utils.py:48-73`

### 怎么实现的
```
/chat/stream → stream_chat()
  ├─ emit(kind,payload) 写入 threading.Queue(src_queue)
  ├─ _run_graph 后台线程(asyncio.to_thread):
  │     set_token_pusher(lambda text: emit("token", text))     # ContextVar 注入
  │     for ev in graph.stream(state, config, stream_mode="updates"):
  │         emit("node_event", ev)                              # 逐节点
  │     结束 emit("__done__")、异常 emit("__error__")
  ├─ _pump 协程：to_thread(src_queue.get) → dst_queue           # 线程→asyncio 桥
  └─ 主生成器消费 dst_queue：
        token → yield {"type":"token"}
        node_event → describe_node() 转中文 → yield {"type":"node"}
        __interrupt__ → yield {"type":"pending"} 并停
        __done__ → 从 checkpoint 取最终态 → yield {"type":"done"}
```

**为什么 graph 放后台线程而不是 async stream**：这是项目踩过的坑（docs/UNDERSTANDING.md:106-107）——langgraph 0.6.x 的 async `astream` + 同步 `interrupt()` 会抛错且 **checkpoint 不落盘**（导致审批无法恢复）。所以改用**同步 stream + asyncio.to_thread** 放线程跑，事件经双队列（threading.Queue → asyncio.Queue）搬运回 asyncio 世界。

**token 流怎么穿过三层**（关键路径）：
```
stream_chat 线程里 set_token_pusher(emit("token"))         # token_stream.py ContextVar
  → agent_node 调 _safe_llm(..., stream_tokens=True)       # llm_utils.py:34
  → _invoke_streaming: llm.stream() 逐 chunk                # llm_utils.py:48-73
  → chunk.content 非空 → pusher(content) → emit → SSE push  # 工具调用轮 chunk 内容为空，天然不推字
  → AIMessageChunk 累加(acc = acc + chunk) 返回完整结果      # 行为与 invoke 一致
```
ContextVar 的意义：pusher 只在"跑图线程"的调用链内可见，不会污染别的线程（多用户并发各自有图线程）。

**为什么 token 流式要看首包延迟**：旧网关首包 15-38s，流式纯负收益；换官方 DeepSeek API 首包 1-3s 才有体验价值（docs/UNDERSTANDING.md:125-126）。**这是一个"做不做某个功能取决于数据/环境"的经典决策案例**。

### 追问
- **SSE 和 WebSocket 区别？** SSE 单向服务器→客户端、基于 HTTP、自动重连、文本；WebSocket 双向、需额外协议。本项目只需要"服务器推过程"，SSE 足够且简单。
- **为什么双队列？** 图在 threading 世界，FastAPI 在 asyncio 世界，Queue 是跨世界传递的线程安全管道；pump 负责搬运。
- **流中断怎么办？** `__done__` 哨兵保证消费循环正常退出（stream_chat.py:133-134）；`_stop_pump` 幂等停泵防线程泄漏（106-112）；token 流中途异常回落 invoke 保最终结果（llm_utils.py:67-69）。
- **pending 事件怎么发的？** node_event 里含 `__interrupt__` → 从注册表找 draft → yield pending（stream_chat.py:142-156）。

## 机制 8：双层安全审核（规则 + LLM）

### 是什么
所有给客户的回复**必须**经过：规则快速拦截（0ms 免费）+ LLM 深度审查（语义级）。防：泄露成本价、隐私、违规承诺、不专业言论。

### 代码在哪
`src/agent.py:121-149` `review_response`；`review_node`（agent.py:338-351）。

### 怎么实现的
1. **规则层**（agent.py:128-135）：敏感词命中（成本价/进货价/拿货价/底价/利润多少/加我微信）→ 若同时"礼貌拒绝（抱歉/不能/无法提供/不方便）+ 无报价数字"则放行（客服正确拒绝不算违规），否则拦截。
2. **LLM 层**（agent.py:137-147）：REVIEW_PROMPT（agent.py:101-118，含"正常报价/确认单电话地址不算违规"的防误杀条款）→ `cheap_llm` 输出 JSON verdict/reason/rewrite；unsafe → 用 rewrite 替换原回复；解析异常 → 放行（fail-open，agent.py:146-147）。
3. 节点层（agent.py:338-351）：只审最后一条 AI 消息；非 AI 跳过；拦截时 `state["messages"][:-1] + [safe]` 替换。

### 为什么这么设计
- **分层成本**：规则层挡掉 80% 简单违规（关键词），LLM 只处理语义级问题；规则错了可直接修，不用调 prompt。
- **fail-open vs fail-closed 的取舍**：LLM 解析失败 → 放行（agent.py:146-147），因为这是"审核第二层"，第一层规则已兜底；真判 unsafe 的概率和误杀成本权衡下选放行（生产可改 fail-closed）。
- **防误杀**：REVIEW_PROMPT 明确列出"不算违规"的白名单（报价、确认单地址电话、回显客户信息），这是给客户展示体验下"能用"的关键（否则客户要个报价都被拦截）。

### 追问
- **为什么审核放在图末而不是 agent 内部？** 图末审核覆盖售前/下单/售后所有出口回复，一处生效（agent.py:515-519 三条路都汇 review）。
- **规则层和 LLM 层谁先？** 规则先：便宜快；规则放行事后再进 LLM。
- **rewrite 是 LLM 生成的，会不会也违规？** 有风险但内置安全 prompt，且规则层会再过一道；生产可对 rewrite 二次校验。
- **如果客户就是要成本价？** 规则层 + LLM 双保险，最终回复是安全版"抱歉，无法提供"。

## 机制 9：有界任务队列（替代裸线程）

### 是什么
把"偏好提取"这类后台任务从"每请求 threading.Thread().start()"改为**固定 worker 的有界队列**。

### 代码在哪
`src/task_queue.py`：`TaskQueue`（26-129）、`get_extraction_queue`（137-149）；使用处 app.py:189-190、agent.py:617-618、stream_chat.py:196-201。

### 怎么实现的
- `queue.Queue(maxsize=200)` + 2 个 daemon worker 线程（task_queue.py:42-61）；
- `submit(fn, *args)`（task_queue.py:83-102）：`put_nowait`，队列满 → 丢弃 + 告警 + 计数 dropped（记忆提取是"尽力而为"，丢了不伤主流程）；
- worker 主循环（task_queue.py:64-81）：取任务 → 执行 → 异常捕获打日志不杀线程 → 计数 processed；
- `metrics()`（task_queue.py:104-113）：submitted/processed/dropped/queued，暴露给 `/healthz`（app.py:263-270，也是 Docker 健康检查探针）；
- `shutdown`（task_queue.py:115-129）：哨兵对象 `_STOP` 通知 worker 退出，join 等收尾。

### 为什么这么设计
- 裸线程无上限 → 高并发线程爆炸；固定 2 worker 线程数恒定。
- 队列有界 → 背压：任务堆积超过 200 直接丢弃告警，而不是无限排队拖垮内存。
- 解耦：主请求不等待偏好提取完成（回复已发出）。
- 单进程下的标准做法；生产跨进程扩缩容换 Redis Stream / Celery / arq，**接口不变**（task_queue.py:10-12）。

### 追问
- **为什么是"丢弃"而不是"阻塞"？** 偏好提取是次要任务，丢一条不影响主链路；阻塞会让用户等。
- **怎么知道队列压力？** /healthz 返回 metrics。
- **丢任务会不会丢偏好？** 会，但偏好是"尽力而为"的增量信息，下轮对话重新提取，可自愈。

## 机制 10：评测体系（三套评测 + 评测驱动改进）

### 是什么
三层验证：单测（66 个 pytest）→ 检索消融（85 题）→ 端到端（11 题规则断言 + LLM-as-Judge 四维评分）。

### 代码在哪
- 用例共享：`src/eval_cases.py`（11 条，含 check 断言）
- 端到端规则：`scripts/eval_agent.py`（走完整图，interrupt 自动 approve 后取最终回复）
- LLM 裁判：`scripts/eval_judge.py`（4 维 1-5 分：relevance/completeness/factual/safety，通过标准 overall≥4 且 factual≥4 且 safety≥4）
- 检索消融：`scripts/eval_retrieval.py`（85 题，对比单路/混合）
- 结果：`eval_results/*.json`；成绩：Hit@3 100%、MRR 0.951、端到端 11/11、Judge 均分 relevance 5.0/completeness 4.55/factual 5.0/safety 5.0/overall 4.82

### 怎么实现的（LLM-as-Judge）
```
case 走完整图 → 拿 reply → judge_question(question, reply)：
  JUDGE_PROMPT（四维打分标准 + "编造订单号=factual 1分/泄露成本价=safety 1分"的硬规则）
  → cheap_llm 输出 JSON → 正则提取 {} → 四维分 + reason
通过 = overall≥4 且 factual≥4 且 safety≥4
```

### 为什么这么设计（★ 面试故事线）
1. **规则断言测不出"质量差"**：关键词在就能过，但"答非所问""信息不全"完全测不出；
2. **加入 LLM-as-Judge 后真的抓到了 bug**：首轮 10/11——裁判指出"知识问答回答过于依赖表格，纯文本下答非所问"；
3. **评测驱动修复**：改了 prompt（agent.py:257-259 知识类问题先给结论再查价 + render_tools.py:143-147 正文不依赖表格）→ 复测 11/11。
> 这是一条完整闭环：**评测 → 发现问题（有证据）→ 修复 → 复测通过**。面试官最爱的"指标驱动"故事。

### 追问
- **为什么会是 10/11？** 那条是"售前-知识问答"（羽绒服用什么面料）：Agent 只调了 render_products 结构化工单，正文没有完整结论，纯文本下答非所问。
- **Judge 是自家模型，会不会自评偏差？** 会（docs/UNDERSTANDING.md:222），缓解：异构模型交叉打分（如 GPT 打分）。
- **规则评测和 Judge 评测怎么分工？** 规则断言是"能不能过"（功能正确性），Judge 是"好不好"（质量）；用例集共享（eval_cases.py）保证两套结果可比。

## 附加机制：结构化展示工具（Render Tools，容易被忽略但值得讲）

**是什么**：让 LLM 在需要展示数据时，通过"假装调用工具"把数据以 JSON 交出来，前端据此渲染表格——解决"LLM 输出非结构化文本、前端没法渲染成表格"的问题。

**代码在哪**：`src/render_tools.py`：三个 schema（PRODUCT_ITEM/ORDER_ITEM/REFUND_ITEM 与数据库字段严格对应）→ `RENDER_TOOLS`（69-126）→ 绑定给 LLM（agent.py:287）→ tool_executor 里"透传"不执行（agent.py:323-327 返回空 ToolMessage）→ 最终态 `extract_render_data`（153-185）取 JSON → done 事件带 data。

**细节**：
- 这是"数据展示协议"，不是真工具：执行返回空字符串，真正价值在 tool_calls 的 args JSON 里（agent.py:323-327）。
- Prompt 强制（RENDER_PROMPT_HINT render_tools.py:134-147）：有产品/订单/退款数据必须调对应 render 工具；但**正文仍要给出可独立理解的结论**（纯文本环境看不到表格）。
- 兜底 `extract_data_from_tools`（render_tools.py:210-263）：LLM 没乖乖调 render 工具时，从 create_order/create_refund 的工具结果解析订单/退款数据——"关键场景必出表格"。

**追问**：为什么不让 LLM 直接输出 markdown 表格？→ markdown 表格无法前端受控渲染 + 字段名可能漂移；JSON Schema 强制字段与库一致，前端按协议渲染，还能存结构化数据。

## 附：面试官深挖的"为什么"汇总（快速过一遍）

| 问题 | 一句话答案 |
|------|-----------|
| 为什么用 LangGraph？ | 状态显式、分支/循环可编排、checkpoint 支持 HITL、stream 可观测 |
| 为什么 Supervisor 分三层？ | 规则省 LLM 调用、稳；LLM 兜底覆盖 |
| 为什么混合检索？ | 向量语义 + BM25 精确词，RRF 融合异构分数，CrossEncoder 精排 |
| 为什么 MCP？ | 工具协议化解耦、最小权限、子进程崩溃隔离 |
| 为什么 interrupt 前要 register_pending？ | 审批列表/挂起守卫/防重复下单都要注册表 |
| 为什么下单 LLM 温度 0？ | interrupt 恢复要重放，必须同输入同输出 |
| 为什么 checkpointer MemorySaver？ | HITL 挂起/恢复的硬前提；进程内版生产换 Postgres |
| 为什么双层审核？ | 规则快免费挡80%，LLM 精；防误杀白名单保证可用性 |
| 为什么后台任务用队列？ | 线程受控、有界背压、尽力而为可丢 |
| 为什么评测要 LLM 当裁判？ | 规则断言测不了质量；且真抓到了 bug，形成闭环 |
| 为什么 render 工具返回空？ | 它是"数据透传协议"，值在 args JSON，不是执行 |
