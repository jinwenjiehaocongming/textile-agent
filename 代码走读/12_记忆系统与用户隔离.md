# 12 · 记忆系统与用户隔离

> 目标：搞懂三层记忆到底怎么分工、user_id 怎么一路贯穿到 SQL 与 Qdrant 的每一行。
> 覆盖 `memory.py`（208 行）的 UserMemory 类与全局注册表、`user_identity.py` 的身份校验、
> `task_queue.py` 的现状、conversations/profile 两张表、以及 06 步反复出现的
> `save_messages` / `save_last_query_type` / `extract_and_store` 到底存去哪。
> 本文会**如实指出** README 声称与代码实际的差异（Redis、后台队列），避免你面试时被追穷。

## 一、先建立心智模型：三层记忆，各管一摊

| 层 | 载体 | 存什么 | 谁写、谁读 | 类比 |
|---|---|---|---|---|
| L1 热缓存 | Redis（**可选**，没起则降级进程内 dict） | 每个会话最近 50 条对话 | 存消息时顺手写；取历史时先查 | 前台随手贴的便签 |
| L2 对话存档 | PostgreSQL `conversations` | 每轮 human/ai 全文（永久） | 每轮结束 `save_messages`；开新轮 `load_recent` | 正式档案柜 |
| L2.5 状态存档 | PostgreSQL `profile` | `last_query_type`（上一轮意图） | 每轮结束写、每轮开始读 | 桌子上的"进行中"便签 |
| L3 长期偏好 | Qdrant `user_memory` | LLM 从对话提炼的身份/联系方式 | 每轮结束后台提取；开头检索注入 | 客户档案卡 |

一句话（README 的"三层记忆" = memory.py 模块注释第 1-9 行的设计）：
**对话历史与即时状态进 PG，长期偏好进 Qdrant，热缓存只是加速，Redis 不在就退化成
内存 dict**。全部带 `user_id`，这就是"多租户从每用户一个文件升级为单库行级隔离"
（memory.py:6-7 注释 / db.py:12-13 注释）。

`UserMemory` 是**每个用户一个档案管家**：拿着同一个 `user_id`，负责该用户所有的
读写——存哪、读哪、带什么过滤条件，都在这一个类里，调用方（app.py / stream_chat.py）
根本不需要知道 SQL。

## 二、user_id 从哪来、谁来把关（user_identity.py 全 36 行）

**事实来源（app.py:72-76 注释，一字不差是重点）**：

```
# ── 用户身份：一律来自 JWT（Authorization: Bearer <token>）──
# 2026-09：去掉 X-User-Id / guest 回退（防任意冒充），无 token 一律 401。
# user["user_id"] 即账号 uuid，行级隔离 key 与 thread_id 顺延用它。
```

也就是说：`users.id`（`uuid4().hex`，32 位无横线）随 JWT 的 `sub` 签发
（02 步），每个受保护端点 `Depends(get_current_user)` 解出 `user["user_id"]`，
**它既是行级隔离 key，又是 LangGraph thread_id**（agent.py:522-524：
`thread_id = user_id`）。

`user_identity.py` 只有一个职责：**统一校验 user_id 格式**。

```python
USER_ID_PATTERN = re.compile(r"^[A-Za-z0-9_-]{1,64}$")   # user_identity.py:16
def is_valid_user_id(user_id) -> bool:
    return isinstance(user_id, str) and bool(USER_ID_PATTERN.fullmatch(user_id))
```

字符集就一句：**1-64 位字母/数字/下划线/连字符，禁路径分隔符与空白**。模块 docstring
（:3-12）写得很清楚：这是从"每用户一个文件"时代防目录穿越（`data/users/../../`）留下的
防御，现在虽是行级隔离，ID 进 SQL/路径前仍统一过一遍。

- 它被**两处**复用（模块 docstring :7-9 自称的"两处"，与代码一致）：
  ① Web 层 `app.py`：`/dev/login` 的 user_id 参数校验（app.py:224-225，非法 → 400）；
  ② 持久层 `memory.py` 的 `sanitize_user_id`（memory.py:198-202）——**任何入口进来的
  user_id 都要再过一次**，非法就告警降级成 `"guest"`，而不是带着脏值拼 SQL。
- `resolve_user_id`（:25-37）目前只有测试在调（历史遗留的"缺省 → guest"解析逻辑）——
  正规账号体系后 Web 入口不再用它。诚实说明，别在面试里说它还在主链路上。

## 三、全局注册表：get_user 是"工厂 + 实例缓存"（memory.py:193-209）

```python
_active_users: dict[str, "UserMemory"] = {}          # 进程内：user_id → 记忆管家

def get_user(user_id: str) -> UserMemory:
    user_id = sanitize_user_id(user_id)              # 非法先降级
    if user_id not in _active_users:
        _active_users[user_id] = UserMemory(user_id) # 首次见才新建
    return _active_users[user_id]                    # 之后永远同一个实例
```

不是每次 new！**同一 user_id 在进程内只有唯一一个 UserMemory 实例**，跨请求共享。
好处：对象轻（只存 user_id），无状态，纯粹是"把 user_id 传给方法的门面"；
坏处（诚实）：dict 在**进程内**无限增长（活跃用户多就占内存），且多 worker / 多实例
部署时每个进程各有一份——一致性靠 PG/Qdrant 兜底，缓存层各管各的。

调用方式（贯穿全文的样板）：

```python
# app.py:98 / :318 / :150 / :281，一模一样的三步
user_id = user["user_id"]                    # ① JWT 解出的身份
memory = get_user(user_id)                   # ② 领该用户的记忆管家
await memory.load_recent(20, session_id)     # ③ 用管家干活（都带 user_id）
```

## 四、L2 对话存档：save_messages 写哪、load_recent 读哪

表结构（db.py:121-134）：

```sql
CREATE TABLE IF NOT EXISTS conversations (
    id         SERIAL PRIMARY KEY,
    user_id    TEXT NOT NULL,
    session_id TEXT NOT NULL DEFAULT 'default',  -- 多会话隔离（2026-09）
    role       TEXT NOT NULL,                    -- human | ai
    content    TEXT NOT NULL,
    created_at TEXT NOT NULL
);
CREATE INDEX idx_conversations_user ON conversations (user_id, id);
CREATE INDEX idx_conversations_session ON conversations (user_id, session_id, id);
```

`save_messages`（memory.py:87-97）做**双写**——热缓存 + PG：

```python
async def save_messages(self, new_messages: list, session_id: str = "default") -> None:
    for m in new_messages:
        if m.type in ("human", "ai"):                          # 只收这两种
            await asyncio.to_thread(_cache_append, self.user_id, {...}, session_id)
            await execute(
                "INSERT INTO conversations (user_id, session_id, role, content, created_at) ...",
                {"uid": self.user_id, "sid": session_id, ...})
```

三个细节：
1. **只落 human/ai**（memory.py:90）——工具调用中间轮不写。历史是"给 LLM 当上下文"
   用的干净问答，工具结果由 LangGraph checkpoint 存（07 步），两边分工。
2. `asyncio.to_thread` 包住同步的 Redis/dict 操作，不阻塞事件循环（memory.py:5 注释
   "改用 to_thread 不阻塞事件循环"）。
3. session_id 贯穿 INSERT——多会话（05 步）让一个用户的不同对话各存各的行。

`load_recent`（memory.py:99-118）就是"每轮对话的上下文来源"（06 步 build_input_state）：

```python
async def load_recent(self, n: int = 30, session_id: str = "default") -> list:
    cached = await asyncio.to_thread(_cache_load_recent, self.user_id, n, session_id)  # ① 先查缓存
    if cached:
        return [...HumanMessage/AIMessage...]
    rows = await query_all(                 # ② 缓存没货 → 查 PG
        "SELECT role, content FROM conversations "
        "WHERE user_id = :uid AND session_id = :sid ORDER BY id DESC LIMIT :n", ...)
    messages = []
    for row in reversed(rows):              # ③ 倒过来 → 时间正序
        messages.append(...)
        await asyncio.to_thread(_cache_append, ...)   # ④ 顺手回填缓存
    return messages
```

读出来直接就是 LangChain 的 `HumanMessage`/`AIMessage` 列表，可作为 state.messages 的
历史前缀（stream_chat.py:29-33：`history = await memory.load_recent(20, session_id)`）。
注意 ③ 的 **ORDER BY id DESC + reversed**：`id` 是 SERIAL 自增，天然时间序；DESC 拿
"最近 N 条"再倒序还原成从旧到新，供 LLM 按时间顺序理解。`WHERE user_id AND session_id`
就是**行级隔离 + 会话隔离**的两把锁。

## 五、L2.5 query_type 存档：为什么必须持久化（profile 表）

```python
# 存（memory.py:127-133）
await execute(
    "INSERT INTO profile (user_id, key, value, updated_at) VALUES (:uid, 'last_query_type', :v, :ts) "
    "ON CONFLICT (user_id, key) DO UPDATE SET value = :v2, updated_at = :ts2", ...)

# 取（memory.py:120-125）
row = await query_one("SELECT value FROM profile WHERE user_id = :uid AND key = 'last_query_type'", ...)
return row["value"] if row else "chat"       # 默认 chat
```

`profile` 是一张 **user_id + key 为主键的 KV 表**（db.py:136-142），这里只用了一个 key：
`last_query_type`。为什么不能只放内存？因为**多轮下单是跨 HTTP 请求的**——客户说"我要
下单"，Supervisor 判定 `place_order` 并把它存下来；客户下一条"嗯对，黑色 500 米"，新请求
的 state 里 `query_type` 必须还是 `place_order`，Supervisor（agent.py:390 起读
state 里的 query_type 决定路由，07 步）才能把消息继续送进下单 Agent。注释原话
（stream_chat.py:178-179）是"关键修复：流式路径此前不持久化 query_type……永远无法
延续到下单 Agent"。每次请求开始时读（app.py:113-116、stream_chat.py:34-43），
跑完把结果写回（app.py:131、stream_chat.py:180-182）。

诚实取舍：这个 key **只有 user 维度、没有 session 维度**——一个用户开两个会话，
上一轮的意图是共享的（会话 A 说"我要下单"，切到会话 B 发消息仍可能被带进下单
流程）。多会话的隔离只管对话历史（conversations.session_id），不管跨轮意图状态。
演示量级能接受，真要严谨应改成 `(user_id, session_id)` 维度或让 session 参与决策。

## 六、L3 长期偏好：Qdrant 怎么存、靠谁提取

### 存储侧（vector_store.py）

单 collection `user_memory`（vector_store.py:31）+ **payload 带 user_id 过滤**，
替代 ChromaDB 时代"每用户一个 collection"的笨办法（vector_store.py:8-9 注释）。
写入（upsert_memory，vector_store.py:125-142）：

```python
point_id = hashlib.md5(f"{user_id}:{text}".encode("utf-8")).hexdigest()  # 幂等 ID
await _run(client.upsert, collection_name=MEMORY_COLLECTION, points=[PointStruct(
    id=point_id, vector=vector,
    payload={"user_id": user_id, "text": text, "timestamp": timestamp})])
```

要点：**id 用 user_id:text 的 MD5**——同一条偏好重复写入是覆盖而不是追加
（注释 :128-129 还记了 qdrant-client 1.19 的坑）；embedding 本地 bge-base-zh 算好，
Qdrant 只存向量 + payload（vector_store.py:11 注释）。

检索（search_memory，vector_store.py:171-181）是 **scroll + payload 过滤**，
"无需向量排序"（注释 :172）——因为偏好只有几十条，直接按 user_id 扫出来：
`scroll_filter=Filter(must=[FieldCondition(key="user_id", match=MatchValue(value=user_id))])`。
这是向量库里的"SELECT * WHERE user_id"。

### 提取侧（memory.py:140-180）：LLM 当档案分析师

```python
async def extract_and_store(self, messages: list, llm) -> None:
    history_text = "\n".join(
        f"{'客户' if m.type == 'human' else '客服'}: {m.content[:100]}"
        for m in messages[-10:])                     # 只看最后 10 条，每条截 100 字
    prompt = f"""你是客户档案分析师。只提取客户基本信息和长期偏好。
只记录客户**原话明确说过**的长期信息：身份、联系方式
严禁记录：颜色偏好（"喜欢黑色"——除非客户明确说 "我只要黑色"）、预算、
任何从订单反向推断的偏好、一次闲聊、问价。
不确定就不要记。宁可漏记不可错记。没有明确信息就输出 SKIP。"""
    resp = await llm.ainvoke([{"role": "user", "content": prompt}])   # cheap_llm
    if result and result != "SKIP" and len(result) > 5:
        for line in result.split("\n"):
            if ...:
                if await vector_store.memory_has_similar(self.user_id, line):  # 去重
                    continue
                await vector_store.upsert_memory(self.user_id, line, ...)
```

值得注意的设计：**宁可漏记不可错记**写进了提示词（:158）。颜色偏好默认不记
（"喜欢黑色"不算，除非"我只要黑色"）、预算不记、从订单反推不记——因为颜色/预算
是会变的短期信息，记错比不记更伤（客服拿错误档案跟客户寒暄很尴尬）。输入只喂
**最后 10 条、每条截断 100 字**（:143-144），控制成本；去重靠 `memory_has_similar`
的向量相似度阈值（vector_store.py:184-201，`score >= 1 - 0.15` 视为重复，:198）。

### 谁触发它？"后台"到底指什么（重要，与直觉不符）

所有调用点都是**事件循环内的后台协程**，不是线程：

```python
# stream_chat.py:185（流式路径）、app.py:137（/chat 路径）、agent.py:640（CLI）
asyncio.create_task(memory.extract_and_store([...], cheap_llm))
```

`cheap_llm`（agent.py:82 起）是便宜模型——提取这种"尽力而为"的活不配用贵模型。
而**读侧**在每次开新轮时同步做：`retrieve_preferences`（memory.py:182-187）
→ 返回字符串列表 → `"；".join` 成 user_context → 注入 system prompt
（agent.py:272-276；app.py:108-110；stream_chat.py:30-31）。
所以对客户的感觉是"隔天再聊，客服还记得我是做羽绒服的"——其实就是把上一轮后台
存进 Qdrant 的偏好捞出来塞进了提示词。

## 七、两个"现状"要诚实交代：Redis 与 TaskQueue

### 热缓存 Redis：代码里有实现 + 优雅降级，但本地通常没跑

README 说"Redis 热缓存（可选）"（README.md:39），memory.py 模块注释自称
"Layer 1: 热缓存 — Redis（毫秒级…）"（:5）。看代码（memory.py:31-45）：

```python
try:
    import redis
    _r = redis.Redis(host="localhost", port=6379, db=0, decode_responses=True)
    _r.ping()
    _use_redis = True
except Exception:
    _r = None
    _use_redis = False
```

**结论：Redis 确实实现了**（import + ping 探活），连不上就**降级为进程内 `_dict_cache`
dict**（:45）并打 warning（:42-43）。用 Redis 时的行为：`rpush` + `ltrim(-50,-1)` +
`expire 3600`（:63-65）——每个会话只留最近 50 条、一小时后过期；dict 版同样只留 50 条
（:67-68）。也就是说：

- 这只缓存**对话历史**（save/load/clear 三处），偏好与 query_type 不走它；
- 本地没起 Redis 时实际跑的是**进程内 dict**——同一进程跨请求有效，但多 worker /
  多实例部署就各有一份、可能读到旧数据（PG 才是唯一真相）；
- 真正把 Redis 跑起来，L1 立刻变成跨实例共享的近 50 条缓存——代码已经写好了，
  只是"可选"。

### 有界任务队列：模块在，但当前没被喂活（task_queue.py 全 149 行）

`task_queue.py` 是标准的**有界线程队列**：默认 maxsize=200、2 个 daemon worker
（:42-62）；`submit` 非阻塞，队列满**直接丢弃并计数**（:83-102）；单任务异常不会杀
worker（:73-81）；带 `metrics()`（submitted/processed/dropped/queued，:104-113）；
`shutdown` 用 `_STOP` 哨兵优雅收尾（:115-129）；全局单例 `get_extraction_queue()`
懒初始化成 `mem-extract` 队列（:137-149）。模块 docstring（:4）说它"替代每请求裸开
threading.Thread（app.py/agent.py/stream_chat.py 原用法）"。

**但按现在的代码搜遍全项目：提交端一个 `submit()` 都没有**——偏好提取全部走
`asyncio.create_task`（上节三个调用点）。`get_extraction_queue()` 全项目只有一处被调用：
`/healthz` 里读它的 `metrics()`（app.py:306-310）。也就是说这个队列**当前是闲置的**
（healthz 上报的是一个永远没任务进出的队列）。原因很好理解：stream_chat.py 头部注释
（:16-17）写明全链路已异步化——提取偏好从"同步函数扔线程"变成了"async 函数起协程"，
协程之间靠 await 让出，不需要线程队列这座桥了。面试被问到就如实说：
**记忆提取当前用 asyncio.create_task（单事件循环内并发、调用方不等它）；有界队列是
异步化之前遗留的通用设施，只还在 /healthz 报指标**——将来任务密度高、create_task
无界会撑内存时，才需要它或 Redis Stream/Celery（task_queue.py:11-12 注释给了替换方向）。

## 八、隔离全景：行级 + 会话级 + 图级

| 维度 | 载体 | 隔离键 | 说明 |
|---|---|---|---|
| 用户 | conversations / profile / Qdrant payload | `user_id` | 所有 SQL 都带 `WHERE user_id = :uid` |
| 会话 | conversations | `session_id` | 同一用户多个对话互不串历史 |
| 意图续轮 | profile | `user_id`（无 session，见第五节诚实取舍） | 跨请求延续 query_type |
| 图/挂起 | LangGraph checkpoint | `thread_id = user_id`（agent.py:522-524） | 审批恢复定位用（08 步） |
| 订单 | orders | `customer_id` | app.py:380-384 `/orders` 也带 uid |

下单/历史订单端点同理（app.py:380-384 `WHERE customer_id = :uid`）——行级隔离不是
记忆系统专利，是整个后端的一贯纪律。

## Q&A

**Q1：为什么偏好提取放"后台"而不是同步做？异步 vs 队列的取舍？**
提取要调一次 LLM（秒级）+ 向量化写入 Qdrant，若同步在回复路径里做，客户每说一句话
都要多等一次慢调用。所以放后台：当前实现是 `asyncio.create_task`（app.py:137、
stream_chat.py:185）——事件循环内起协程，调用方不等它、它自己 await 让出。
选 create_task 而非线程队列的原因：全链路异步后提取是纯 async 函数，await 天然
并发安全，不需要线程；且提取是**尽力而为**（提取失败只 log 不报错，memory.py:179-180；
memory_has_similar 异常返回 False，vector_store.py:199-200），丢了也不影响主流程。
代价（诚实）：create_task 无界——极端高并发下积累的任务会占内存；任务队列模块
（task_queue.py）虽是为此设计的，但当前闲置（见第七节）。生产兜底思路：限流、
有界队列、或升级 Redis Stream/Celery。

**Q2：多会话下记忆怎么保证不串？有没有"串"的地方？**
对话历史不串：`conversations` 按 `(user_id, session_id)` 双键隔离（db.py:121-134），
`load_recent(limit, session_id)` 的 WHERE 带两个条件（memory.py:106-109），app.py 的
`_resolve_session` 还校验会话归属、非本人会话直接 404（app.py:84-89）。会话切换时
前端重新拉该会话历史（13 步），消息互不污染。
会"串"的是**跨轮状态**：`last_query_type` 存在 profile 里只有 user 维度（memory.py:127），
会话 A 排队下单中切到会话 B 发消息，B 也会继承 `place_order`；长期偏好（Qdrant）同样
按 user 聚合不按会话。所以严格说：**"记录"按会话隔离，"画像与意图"按用户共享**——这在
单客户多会话场景是合理简化（偏好本来就该跨会话），但下单续轮跨会话时靠挂起态守卫兜底
（stream_chat.py:77-83 检测到该用户有待审批订单就只提示不跑图）。面试能主动说出这条
边界是加分项。

**Q3：热缓存 Redis 到底实没实现？README 和代码矛盾吗？**
不矛盾，但要讲清"可选"两个字的分量：memory.py:31-38 **真写了 Redis 分支**
（import + ping 探活 + decode_responses），连不上就降级成进程内 dict（:36-45）。
所以代码层面 Redis 热缓存是**实现好的能力**，行为细节也齐：list 只留最近 50 条
（ltrim）、1 小时过期（expire 3600，:63-65）。本地/演示环境通常没起 Redis，
实际跑的是 dict 版（启动日志会打 "Layer 1 热缓存: Dict (Redis 未运行)"，:42-43）。
局限要承认：dict 版跨进程无效（多 worker 读到的是各自的 50 条），缓存与 PG 之间无
显式失效协议（靠 TTL 兜），且它只缓存对话历史，偏好不经过热缓存。README 写"可选"
正是因为降级路径是设计的一部分。

**Q4：LLM 提取用户偏好，可靠性怎么保证？幻觉了怎么办？**
项目用三道闸：① 提示词红线——"只记录客户原话明确说过的""严禁从订单反推""宁可漏记
不可错记""不确定输出 SKIP"（memory.py:146-158）；② 去重——`memory_has_similar`
向量相似度阈值（vector_store.py:184-201）防同一偏好反复写入膨胀 collection；
③ 失败静默——LLM 调用/写入异常只 warning（memory.py:179-180），绝不影响主流程。
但可靠性上限是 LLM 的：提取结果没有人工审核回路，模型记错的东西会一直躺在
payload 里并随 user_context 注入每次对话。诚实取舍：演示量级接受"少记优于错记"
的提示词策略；生产要给偏好加**来源时间戳 + 人工可删/可标错**的管理界面，
甚至对"高风险断言"（如联系方式）强制客户确认后才入库。

**Q5：为什么对话历史要拆成 role/content 两列，而不是整条序列化存 JSON？**
职责不同：conversations 是给"重新拼上下文"用的，查询要按 `user_id`/`session_id`/
时间范围过滤和分页——拆成行才能走索引（db.py:129、134 两个联合索引），JSON 大字段
没法这么查。代价（诚实）：只能存 human/ai 两类（memory.py:90），工具调用过程、思考
链这些细节在 PG 里没有——但它们由 LangGraph checkpoint（MemorySaver）按 thread 全量
保存（agent.py:557-558），两套存储分工：**checkpoint 保"图怎么走到这"，conversations
保"客户看过什么"**。另一个代价是 created_at 存 ISO 字符串（SQLite 迁移遗留约定，
见 02 步 Q6），排序靠自增 id 而非时间列。

**Q6：get_user 为什么缓存实例而不是每次新建？多实例部署会怎样？**
UserMemory 本身无状态（只存 user_id），缓存的价值不在省构造，而在**语义统一**：全进程
只有一份"该用户档案管家"，任何调用方拿到的都是同一个对象，将来若加进程内缓存字段
不会出现两份不一致。多实例部署下每实例各有一份 `_active_users`——这不影响正确性，
因为所有数据读写都落在 PG/Qdrant（每实例的 dict 只是门面），Redis L1 若启用倒是
跨实例共享的。真正的隐患只有一个：进程内 dict 只增不减，长时间运行 + 海量 user_id
会占内存——生产可换成 LRU 或干脆去掉缓存层。

**Q7（追问）：既然是 JWT sub 当 user_id，为什么还要 user_identity 这套校验？**
纵深防御。JWT 验签保证"token 是真的"，但角色/内容可能来自 /dev/login 这类宽松签发口
（app.py:219-227 允许任意合法 user_id 伪造身份——仅 DEV_MODE）；而 user_id 会被拼进
SQL 命名参数、Qdrant 过滤、以及（历史遗留的）文件路径。`sanitize_user_id`（memory.py:196-202）
保证**任何入口进来的值**都先过字符集闸门，非法就降级成 guest 而不是带病执行——哪怕
未来有人新加一个端点忘了校验，持久层这一道也兜得住。字符集 `[A-Za-z0-9_-]{1,64}`
本身是"每用户一文件"时代的防目录穿越遗产（user_identity.py:3-6），如今行级隔离下
已无路径风险，但保留它让 user_id 永远可作为安全的 key/文件名使用——这套"一层不信
一层、永远兜底"的思路正是面试官想听的。
