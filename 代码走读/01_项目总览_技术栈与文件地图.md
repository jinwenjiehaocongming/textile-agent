## 一、先建立心智模型

一句话定位：**一个纺织 B2B 交易智能体（Agent）**。客户说人话：
「羽绒服用什么面料」「T400 黑色多少钱」「我要退货」——系统自动路由到售前 / 下单 / 售后
三个 Agent，跑通 **询价 → 知识问答 → 下单（人工审批）→ 查单 → 退款** 的完整交易闭环。

> 不是"回答问题"的客服，是"完成业务"的 Agent——区别在于它会**调用工具、写数据库、
> 走人工审批**，而不是只回一段文字。

技术栈（README 徽章 + requirements.txt）：

| 层 | 选型 | 干什么 |
|---|---|---|
| 语言 | Python 3.12（>=3.10） | 后端全异步 |
| Agent 编排 | LangGraph 0.6 | 状态机图：节点 + 边 + interrupt 挂起 |
| Web 框架 | FastAPI | HTTP 接口 + SSE 流式 |
| 向量库 | Qdrant（LocalMode / 独立服务双模式） | 语义检索，集合 `textile_knowledge`（142 条） |
| 关键词检索 | BM25（rank_bm25） | 精确匹配兜底 |
| 融合/重排 | RRF 融合 + CrossEncoder Rerank（可选开关） | 提升检索精度（MRR 0.959） |
| 业务库 | PostgreSQL 16 + SQLAlchemy async + asyncpg | 产品 281 条 / 订单 / 退款 / 对话 / 用户 / 审计 |
| LLM | DeepSeek（OpenAI 兼容接口 ChatOpenAI） | 意图分类、回答、审核、偏好提取 |
| 工具层 | 官方 MCP SDK（FastMCP 三 server） | product / order / refund |
| 前端 | React + Vite + Tailwind（玻璃拟态） | 聊天 UI、审批面板、订单列表 |
| 部署 | Docker Compose（app + postgres + qdrant）+ GitHub Actions | 一键起服务 + CI |

## 三、架构图（README 的 mermaid，翻译成人话版）

```
客户消息
  → [改写查询 rewrite]          把口语整理成适合检索的问句
  → [知识检索 retrieve]         Qdrant+BM25+RRF+Rerank，必走一步
  → {Supervisor 路由}           LLM 判断意图
      ├─ 售前 → 答询价/知识/库存  （agent.py 内）
      ├─ 下单 → 查产品→确认单→⚠️ interrupt 挂起 等销售经理审批 → 写订单
      └─ 售后 → 查订单 → 对照退货规则 → 生成退款工单
  → [双层审核 review]           规则快速拦截 + LLM 安全审查（所有回复必过）
  → SSE 逐字推回前端
```

存储版一句话：业务 → PostgreSQL；知识 → Qdrant `textile_knowledge` + BM25；
Embedding/Rerank → BAAI bge 本地模型（HF 缓存，Docker 可选下载）；记忆 → PG + Qdrant 偏好。

## 五、怎么跑起来（三层）

```bash

docker compose up --build
```

## Q&A

**Q1：这个项目和普通"聊天机器人"的本质区别？**
普通客服机器人 = 问题 → 检索 → 回一段话。本项目是 **Agent**：回复只是副产品，
重点是**完成业务动作**——下单 Agent 会把订单写到 PostgreSQL（但要销售经理人工审批），
售后 Agent 会生成退款工单。区别在"会不会用工具改变系统状态 + 有没有人机协作（HITL）"。

**Q2：为什么把代码拆成 app.py 和 src/？**
app.py 只做 **HTTP 翻译**（收请求、验身份、翻译状态码、发 SSE）；真正业务全在 src/。
好处：业务代码不认识 HTTP（可以脱离 Web 跑：`python src/agent.py` 终端直接对话、
评测脚本直接调用），换框架 / 加 CLI / 加 WebSocket 都不动业务。分层即解耦。

**Q3：一条消息最少要过几个模块？**
前端 → app.py（验 token、定会话）→ memory（加载历史）→ agent.py 图
（rewrite → retrieve → supervisor → 对应 agent → review）→ stream_chat 收尾存档 →
SSE 回前端。第 06/07 步逐层展开。

**Q4：PostgreSQL 和 Qdrant 各存什么？为什么两个库？**
PG 存**结构化业务数据**：产品/订单/退款/对话/用户/审计（要事务、要 SQL 查询、
要行级隔离）。Qdrant 存**非结构化知识的向量**：142 条纺织知识切片的 embedding，
做相似度检索。两类数据形态完全不同，各用各的引擎是标准做法；
BM25 关键词索引落在本地文件（index/）里，不需要额外服务。

**Q5：仓库里 面试/、docker-hello/、问题.md 是什么？能删吗？**
学习性杂项：`面试/` 是面试整理笔记、`docker-hello/` 是最小 Docker 练习示例、
`问题.md` 记录代码细节心得。不影响主程序运行，但**别提交到生产分支**——
主程序只依赖 app.py / src / scripts / web / data / index / requirements.txt 等。

**Q6（追问）：为什么要"全部异步"？**
聊天请求要等 LLM（几秒~几十秒）和数据库（毫秒级）。同步写法下，一个慢请求会
**占死一个工作线程**，服务器并发能力被线程数卡死；asyncio 单线程事件循环在
`await` 等待时去服务别的请求，用少量线程扛大量慢 IO。本项目全链路
（FastAPI → db → MCP → LangGraph → LLM astream）都是 async，是"企业级演进"的核心之一
（第 03 步细讲语法）。
