# 05 · 多会话与聊天记录

> 目标：搞懂三件事——**为什么能同时开多个对话？历史存在哪、怎么按会话取回？
> 会话属于谁、怎么防止你打开别人的对话？**
> 覆盖 sessions/conversations 两张表、老库升级的 ALTER 逻辑、
> `_resolve_session` 归属校验、四个 CRUD 端点、`/history` 与自动命名。
> 前端何时调用只点到为止（App.jsx 一句带过，13 步细讲）。

---

## 一、先建立心智模型：从"一个用户一个聊天记录"到"一个用户一堆会话"

最早版本里，一个用户只有**一条**聊天记录：消息表加一列 `user_id`，取历史就是
`WHERE user_id = ?`。问题：客户上午问羽绒服面料、下午要下单、晚上来退货，
全挤在一条时间线里；记忆互相污染——上一单的上下文会串进下一单。

多会话改造 = 在 `user_id` 之外再加一层 `session_id`（会话），像给聊天记录
**加了个文件夹**：

| 概念 | 类比 | 代码里的实体 |
|---|---|---|
| 用户 | 一个人 | `user_id`（uuid，JWT 里来） |
| 会话（session） | 这个人开的"对话窗口" | sessions 表一行，`id` = `session_id` |
| 消息 | 窗口里的每句话 | conversations 表一行，标着 `(user_id, session_id)` |
| 遗留会话 | 改造前的旧窗口 | `session_id = 'default'`，特殊放行 |

两个"门面"文件的分工：
- `src/sessions.py`：**会话元数据**（列表/新建/改名/删除/归属校验），只管 sessions 表；
- `src/memory.py`：**消息本身**（落库、取回），按 `(user_id, session_id)` 读写 conversations 表。

`app.py` 只做 HTTP 翻译：从 JWT 拿 `user_id` → 从请求拿 `session_id` →
先过归属校验（`_resolve_session`）→ 再放行到业务函数。

## 二、两张表与索引（src/db.py）

### conversations：消息本体（db.py:121-128）

```sql
CREATE TABLE IF NOT EXISTS conversations (
    id         SERIAL PRIMARY KEY,                -- 单调递增，排序靠它
    user_id    TEXT NOT NULL,
    session_id TEXT NOT NULL DEFAULT 'default',   -- 多会话隔离（2026-09）
    role       TEXT NOT NULL,                     -- human | ai
    content    TEXT NOT NULL,
    created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_conversations_user ON conversations (user_id, id);        -- 129
```

逐词看：
- `id SERIAL`：数据库自增整数。**取历史排序靠 `id` 而不是 `created_at`**——
  因为 `created_at` 是 ISO 文本串（从 SQLite 时代继承的约定，02 步 Q6 吐槽过），
  同一秒内多条消息文本串排序不稳，自增 `id` 保证先写先排。
- `session_id DEFAULT 'default'`：新老代码两用——老代码 INSERT 不带 session_id 也能落库；
- 两个索引都带 `user_id` 打头：索引前缀匹配，天然保证"按用户查"走索引。

### 老库升级：ALTER TABLE 补列（db.py:131-134）

```sql
-- 老库升级（幂等）：无 session_id 列的 conversations 补列（存量数据归入 'default'）
ALTER TABLE conversations ADD COLUMN IF NOT EXISTS session_id TEXT NOT NULL DEFAULT 'default';

CREATE INDEX IF NOT EXISTS idx_conversations_session ON conversations (user_id, session_id, id);
```

为什么 CREATE TABLE 里明明已有 `session_id`（db.py:124），还要 ALTER？
因为 **`CREATE TABLE IF NOT EXISTS` 对已存在的表是空操作**——多会话上线前建的
老表根本没有这一列，必须用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 补上，
`DEFAULT 'default'` 让存量消息全部自动归入遗留会话。这就是注释里"老库升级（幂等）"
的含义：同一份 SCHEMA_SQL 跑一万遍结果都一样（PostgreSQL 9.6+ 支持
`ADD COLUMN IF NOT EXISTS`）。执行方式也顺手看下（db.py:176-181）：
`ensure_schema()` 把整段 SQL 按 `;` 切开、逐条执行，包在一个事务里。

新索引 `idx_conversations_session (user_id, session_id, id)`（db.py:134）：
多会话查询长这样 `WHERE user_id=? AND session_id=? ORDER BY id ...`，这个复合索引
**前缀 + 排序三列全中**，是专门为新查询模式建的（旧索引 `(user_id, id)` 覆盖不了
`session_id` 过滤，会退化成过滤后排序）。

### sessions：会话元数据表（db.py:165-172）

```sql
CREATE TABLE IF NOT EXISTS sessions (
    id         TEXT PRIMARY KEY,      -- session_id（uuid4 hex）
    user_id    TEXT NOT NULL,
    title      TEXT NOT NULL DEFAULT '新对话',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_sessions_user ON sessions (user_id, updated_at);
```

注意 **`'default'` 不在 sessions 表里**：它是遗留会话，不是用户主动建的窗口，
所以列表查询看不到它（sessions.py:49 docstring：「不含 'default' 遗留会话」）。
`sessions.id` 是 `uuid.uuid4().hex`（sessions.py:38），跟 user_id 同一风格（02 步），
防枚举、对外安全。

## 三、归属校验：`_resolve_session`（app.py:84-89）

```python
async def _resolve_session(user_id: str, session_id: str) -> str:
    """解析并校验会话归属：'default' 始终放行（历史数据），其余必须属于该用户。"""
    sid = (session_id or "").strip() or "default"
    if sid != "default" and not await get_owned_session(user_id, sid):
        raise HTTPException(status_code=404, detail="会话不存在")
    return sid
```

这是所有"带会话"端点（/chat、/chat/stream、/history）的**第一道闸**。逐行拆：
1. 空串/缺省 → `"default"`：老客户端不发 session_id 也能用（兼容）；
2. **不是 default 就必须通过 `get_owned_session`**——它的 SQL 是（sessions.py:28-34）：

```python
"SELECT ... FROM sessions WHERE id = :sid AND user_id = :uid"
```

`user_id` 来自 JWT，**用户拿别人的 session_id 来查 → 查无此行 → None → 404**。

面试高频题：为什么是 404 不是 403？两说：
- 403 语义是"我知道你是谁，但你没权限"——这等于**承认这个资源存在**；
- 404"会话不存在"把"不存在"和"不是你的"混成一个答案，**不泄露任何会话是否存在**，
  跟登录接口"用户名或密码错误"一个套路（02 步）。
  资源隔离场景下，宁可一律说"没有"，也别让人探测到别人的会话 id。

删除/改名同样双保险：先 `get_owned_session` 判存在，SQL 再带 `AND user_id = :uid`
（sessions.py:62-72, 75-84）——即使第一道漏了，UPDATE/DELETE 的 WHERE 也写不到别人的行。

## 四、会话 CRUD 四个端点 → sessions.py（app.py:346-370）

| 端点 | app.py | sessions.py | 说明 |
|---|---|---|---|
| `GET /sessions` | 346-349 | `list_sessions` 48-59 | 该用户全部会话，`ORDER BY updated_at DESC` 最近活跃在前，上限 50 |
| `POST /sessions` | 352-355 | `create_session` 37-45 | 新建，title 可空，`uuid4().hex` 当 id |
| `PATCH /sessions/{sid}` | 358-363 | `rename_session` 62-72 | 改名；不属于你 → 404 |
| `DELETE /sessions/{sid}` | 366-370 | `delete_session` 75-84 | 先删消息再删会话；不属于你 → 404 |

共同前提：`user: dict = Depends(get_current_user)`——**先验身份，再谈会话**，
owner 隔离的第一层是"user_id 只能从 token 来"，请求体里传什么都没有用。

删除逻辑值得多看一行（sessions.py:75-84）：先 `DELETE FROM conversations WHERE user_id AND session_id`，再删 sessions 行——**消息是会话的孩子，先清孩子再删爹**。
诚实取舍：这两句各走一个独立事务（db.py 的 `execute` 是单条自动事务，db.py:70-74），
不是原子的——第二句失败会留下一个"空会话"孤儿行。概率极低，演示量级可接受，
生产会包一层事务（`get_engine().begin()` 手动 begin）。

## 五、会话标题：首条消息自动命名（sessions.py:87-103）

```python
async def touch_session(user_id: str, session_id: str, preview: str = "") -> None:
    """消息落库后调用：更新时间戳；若是「新对话」且首条来了 → 自动取标题。"""
    if session_id in ("", "default"):
        return            # default 不在 sessions 表，跳过
    ts = _now()
    if preview:
        await execute(
            "UPDATE sessions SET title = CASE WHEN title = :dft THEN :pv ELSE title END, "
            "updated_at = :ts WHERE id = :sid AND user_id = :uid",
            {"dft": DEFAULT_TITLE, "pv": (preview.strip() or DEFAULT_TITLE)[:MAX_TITLE_LEN], ...})
    else:
        await execute("UPDATE sessions SET updated_at = :ts WHERE id = :sid AND user_id = :uid", ...)
```

三件事：
1. **更新 `updated_at`** → 会话列表按它倒序，活跃会话浮到顶部（第四节）；
2. **自动命名**：SQL 里 `CASE WHEN title = '新对话' THEN 新标题 ELSE 原标题 END`——
   只有标题还是默认值（`DEFAULT_TITLE = "新对话"`，sessions.py:20）时才改，
   preview 是这条消息的前 18 字（`MAX_TITLE_LEN = 18`，sessions.py:21）——
   **用户手动改过的名字不会被后续消息顶掉**（条件只在"还没起名"时成立）；
3. `"", "default"` 直接 return：遗留会话不在表里，不用管。

谁调用它？`/chat` 和流式路径都在消息落库后调
（`app.py:127/136` 传 `req.message`；stream_chat 里是 `_touch`，`stream_chat.py:196-204`）。
所以"后端自动命名、前端免维护"（sessions.py:10 docstring）——前端新建会话时
title 留空（App.jsx `createSession()` 不带参数），第一条消息一发，标题自己长出来。

## 六、消息落库与取回（src/memory.py，细节 12 步展开）

落库（memory.py:87-97）：`save_messages` 把 human/ai 消息逐条写两处——
① 热缓存（Redis，key 形如 `chat:{user_id}:{session_id}`，memory.py:48-49，
没有 Redis 时降级成进程内 dict），② PostgreSQL `conversations` 表。**session_id 全程带着**。

取回（memory.py:99-118）：`load_recent(n, session_id)` 是两条消息路径共同的取数函数：

```sql
SELECT role, content FROM conversations
WHERE user_id = :uid AND session_id = :sid
ORDER BY id DESC LIMIT :n        -- 先取最新 n 条（倒序）
```

代码拿到倒序结果后 `for row in reversed(rows)`（memory.py:112）再翻回**正序**——
倒序 LIMIT 是为了只取最新 30 条，翻正是为了让消息数组按时间先后喂给 LLM。
Redis 命中就直接返回缓存（同样是正序），没命中才查 PG 并回填缓存。

两个数量级别搞混（面试容易踩）：

| 调用点 | 取多少条 | 目的 |
|---|---|---|
| `/history` 端点（app.py:146-152） | `load_recent(30)` | 前端展示聊天记录 |
| `/chat`、`/chat/stream` 开头（app.py:108 / stream_chat.py:29） | `load_recent(20)` | 喂给 Agent 当上下文（控制 token 成本） |

`/history` 还顺手做了角色翻译：`{"role": m.type, "content": m.content}`
（`m.type` 是 `human/ai`，前端要 `user/ai`，App.jsx 里再映射一次）。

前端什么时候调？（一句话，13 步细讲）登录成功后 `fetchSessions` 拉列表，
**列表为空就自动 `createSession`**（App.jsx:108-133）；切换会话时 `fetchHistory(sid)`
重载消息（App.jsx:185-201）。也就是说新用户一进来就会被"塞"一个空会话——
这就是为什么你会看到后端 sessions 表总有用户的第一个会话。

## Q&A

**Q1：为什么历史排序用自增 `id`，而不用 `created_at`？**
`created_at` 是 ISO 文本串，同秒多条时字符串排序不稳定；且它是应用层时间，
时钟回拨/手动改库都会乱序。`id SERIAL` 是数据库保证的写入顺序，先写的小、后写的大，
`ORDER BY id DESC LIMIT n` 一定取到"最新 n 条"，再 `reversed` 翻回正序喂给模型。
面试延伸：生产里聊天表常用 `(user_id, session_id, id)` 的复合索引 + `id` 排序，
就是因为自增主键天然是时间序的替身。

**Q2：用户拿别人的 session_id 调 /history，会发生什么？**
先过 `_resolve_session`：`get_owned_session(别人_id, 你的token)` 的 SQL 同时要求
`id = 别人的sid AND user_id = 你的uid`，查无此行 → **404「会话不存在」**。
注意不是 403：403 等于承认"有这个东西但你不许看"，反而泄露资源存在性；
404 把"不存在"和"不是你的"混成一句话，是最干净的隔离答案。改名/删除同理
（sessions.py:62-84 的 `AND user_id = :uid` 是第二层保险）。

**Q3：`'default'` 是什么？为什么它被特殊放行又不出现在会话列表？**
它是多会话功能上线**之前**的老数据：老表没有 session_id 列，迁移时
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS session_id TEXT NOT NULL DEFAULT 'default'`
（db.py:132）让存量行自动归入 `'default'`。它不是用户主动建的窗口，sessions 表里
没有它，所以列表不展示（sessions.py:49）；但老客户端不带 session_id 的请求
（`ChatRequest.session_id` 默认 `""`）还要能用，所以 `_resolve_session` 对
`'default'` 一律放行（app.py:84-89）。诚实取舍：老用户的 default 历史在 UI 上
看不到入口（列表被新会话占了），只能算"兼容兜底"，不是完整迁移方案。

**Q4：会话标题是前端传的还是后端起的？起名的规则是什么？**
新建时前端可传可不传（App.jsx `createSession()` 默认空）；真正的自动命名在后端：
消息落库后调 `touch_session`（app.py:127/136），SQL 用
`CASE WHEN title = '新对话' THEN 首条消息前18字 ELSE title END`（sessions.py:93-98）
——**只有标题还停在默认值才改**，所以首条消息决定名字、用户手动改过不再被覆盖、
`'default'` 会话直接跳过（不在表里）。18 字截断（sessions.py:21）保证侧栏不换行。
如果首条消息是空的，退回默认标题（`(preview.strip() or DEFAULT_TITLE)[:18]`）。

**Q5：`conversations` 和 `sessions` 两张表为什么不合成一张？**
职责不同、生命周期不同：sessions 一行 = 一个会话**元数据**（标题、活跃时间），
conversations 一行 = **一条消息**。会话可以被删掉（连消息一起），但消息不能反过来
决定会话存在。而且 `'default'` 这种特殊值只存在于"消息侧"——把两者合并就
没法表达"有消息但没会话行"的遗留状态。这也是"元数据表和明细表分离"的通用建模。
（查询则靠 `idx_conversations_session (user_id, session_id, id)` 一个索引顶住，
db.py:134。）

**Q6：`/history` 取 30 条、Agent 上下文只取 20 条，为什么不一致？**
面向对象不同：30 条是给**人看**的（UI 翻记录，多给点无妨）；20 条是给 **LLM 看**的
——每条消息都要进 prompt，塞得越多 token 越贵、越长越容易"记岔"（注意力漂移）。
取最近 20 条只是经验值。面试可补一句：真正的生产方案是"摘要 + 窗口"分层记忆
（远的历史压缩成摘要，近的保留原文），本项目 12 步的记忆系统是另一个方向的探索。

**Q7：多会话上线，老库的 conversations 表没有 session_id 列，怎么平滑升级？**
靠幂等 Schema：`CREATE TABLE IF NOT EXISTS` 对老表空操作 → 紧跟
`ALTER TABLE ADD COLUMN IF NOT EXISTS session_id TEXT NOT NULL DEFAULT 'default'`
补列并把存量归 default → 再建新索引 `idx_conversations_session`（db.py:121-134）。
整段 SCHEMA_SQL 被 `ensure_schema()` 按 `;` 拆分、单事务执行（db.py:176-181），
跑多少次都安全。这就是"迁移脚本幂等"的标准姿势：上线跑一次不报错，CI/本地重复跑也不报错。

**Q8（追问）：会话删除不是原子的（两句 DELETE 各一个事务），会有什么后果？**
`delete_session`（sessions.py:80-83）先删 conversations、再删 sessions，
中间若第二次失败，会留下一个没有消息的孤儿会话行（列表里一个空窗口，删不掉
重删即可）。量级上概率极低，所以代码注释写"软业务场景可接受"。标准修法是
包一层显式事务（`async with get_engine().begin()`）或干脆外键
`ON DELETE CASCADE`——面试说出"我知道这里可以更严谨、为什么没做"，比假装没问题强。
