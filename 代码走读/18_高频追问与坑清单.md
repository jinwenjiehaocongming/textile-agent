## 三、最容易翻车的 5 个"概念混淆"（说错立刻露馅）

1. **认证 vs 授权**：401 没证明你是谁；403 认识你但没资格。
2. **token 的三重含义**：登录 JWT（门禁卡）≠ LLM token（生成的字块）≠ 图中"状态更新"
   —— 嘴上分清，代码里是三个东西。
3. **SSE vs WebSocket**：SSE 服务器单向推、基于 HTTP、自动重连；WebSocket 双向。
   本项目的"打字机"用 SSE 足够（只需服务器→浏览器）。
4. **向量检索 vs 关键词检索**：语义相似 ≠ 字面命中；RRF 是融合不是排序模型。
5. **interrupt vs 普通 return**：interrupt 会**落盘挂起**（checkpoint），可被
   `Command(resume=...)` 唤醒继续跑；不是"发个消息等下次"。

## 四、讲项目时的"一页话术"（30 秒版 → 2 分钟版）

**30 秒**：我做的是一个纺织 B2B 交易智能体——客户用自然语言询价/下单/退货，
系统用 LangGraph 编排"改写→混合检索→意图路由→三 Agent 干活"的图，下单走到
人工审批（HITL interrupt），回复全部过双层审核并经 SSE 逐字推给前端；业务数据在
PostgreSQL，知识检索是 Qdrant 向量 + BM25 + RRF + Rerank，工具层是三个官方 MCP SDK
子进程，鉴权是 JWT 账号体系。

**2 分钟**（加演进与取舍）：这个项目是从演示客服机器人一步步演进来的——存储从
SQLite/ChromaDB 迁到 PostgreSQL/Qdrant（并发与独立服务），调用从同步线程桥迁到
全链路 asyncio（单事件循环），工具从函数直调迁到官方 MCP SDK（子进程标准化），
身份从 X-User-Id/开发登录迁到正式 JWT 账号体系（防冒充+审计），还加了多会话、
评估体系（检索消融 85 题、端到端 25 题、LLM-as-Judge 11 题全绿）和 Docker/CI。
每一步我都知道当时的动机和留下的取舍，比如 JWT 无法吊销、登录无限流、Rerank
默认关、审批注册表在内存——生产化清单里都列了对应方案。

## 2026-09 修复过程中真踩到的坑（值得单独记）

| # | 坑 | 症状 | 教训 |
|---|---|---|---|
| 1 | **`query_one` 执行 UPDATE 不提交** | `UPDATE users SET token_version = token_version + 1 ... RETURNING` 写成了 `query_one`（走 `connect()` 不提交）→ SQLAlchemy 2.0 commit-as-you-go，连接关闭即**静默回滚**。接口返回 200、日志打了"凭证已作废"，但数据库根本没变 → **封号形同虚设** | 命名会骗人：`query_one` 看起来只是"查一行"，拿它跑写语句不会有任何报错。要么用 `execute()`（`begin()` 提交），要么用我新加的 `execute_returning()`。**测试必须断言"副作用真的落库了"**，只断言状态码一定会漏掉这类 bug |
| 2 | **宽限窗把重用检测吞掉** | 轮换竞态宽限写成 `now - prev_at <= leeway`：leeway=0 时"同一秒内的重放"永远算并发刷新，重用检测形同虚设 | 时间窗一律左闭右开（`<`）；边界值要用测试钉死，别等安全评审时才发现 |
| 3 | **`await` 优先级写错** | `assert (await c.post(...).status_code) == 401` → `await` 绑到了属性访问上，报 `'coroutine' object has no attribute 'status_code'` | 括号要包住整个调用：`(await c.post(...)).status_code`。写测试时这种错一眼看不出来 |
| 4 | **测试与基础设施耦合** | `test_sessions.py` 借 `/auth/register` 拿 token → 登录改成 fail-closed 后，Redis 一没，**"聊天会话"的测试整片失败** | 测试要按"被测对象"取依赖：测会话就直接建账号+签 token，别顺路走登录流程 |
| 5 | **缓存污染型 flaky** | PG 被 `reset_schema` 清空、Redis 没清 → 上个用例的缓存变成"第二个真相来源"，`test_user_isolation` 随机红 | 清数据要**连缓存一起清**（conftest 里 autouse 清 `study1:chat:*` / `:auth:*` / `:rl:*`）；限流桶更是跨用例共享状态 |


| 6 | **SSE 端点里限流写在建流之后** | `/chat/stream` 一旦返回 `StreamingResponse`，状态码就锁成 200，429 只能塞进事件里 → 前端拿不到状态码、也读不到 `Retry-After` | 限流/鉴权这类"入口判定"必须在**建立流之前**完成；同理 401 也要在流外处理 |
| 7 | **兜底 `except Exception` 吞掉限流异常** | `/chat` 有 `except Exception` 把 `RateLimited` 转成 200 + "系统异常…"，客户端永远看不到 429 | 入口级的横切逻辑（限流、鉴权）要么放在 try 之外，要么在 except 里显式 `raise`。**这次是测试抓出来的**——断言 429 才暴露出来，断言"有回复"就会漏 |


| 8 | **`reset_schema()` 漏删新建的表** | 新增 `pending_approvals` 后忘了加进 `reset_schema` 的 DROP 列表 → 上一个用例的待审批行漏到下一个用例，出现"单跑绿、整跑红"。**这次又踩了一次**（上次是 Redis 缓存、这次是 PG 表） | 加表/加缓存命名空间时，**必须同步更新测试隔离的清理清单**；发现"整跑红单跑绿"先怀疑跨用例污染 |
| 9 | **守卫写在 `if snap.next:` 里面** | SSE 路径的挂起态守卫原本嵌在"图有下一个节点"的分支里 → 重启后 `next` 为空，守卫直接失效，客户再发消息会让图从头跑一遍，把丢失悄悄掩盖成"重新下单" | 判定条件要基于**业务真相来源**（PG），而不是"另一个状态的副作用"；辅助条件只能用来加强，不能用来开门 |

## 管理端工作台（2026-09）踩过的坑

- **幂等 DDL 也有顺序语义**：`ALTER TABLE refunds ADD COLUMN IF NOT EXISTS ...` 写在
  `CREATE TABLE IF NOT EXISTS refunds` **之前** → 开发库（表已存在）正常，
  空测试库直接 `relation "refunds" does not exist`。判断标准只有一个：**在空库上从零初始化一遍**。
- **加了 JOIN 的条件要同步到计数查询**：关键词搜索加了 `u.display_name ILIKE :kw`，
  只改了列表查询没改 `count(*)` → `missing FROM-clause entry for table u`。
  （列表能出、总数报错，或反过来，都是这个原因。）
- **`audit_log` 刻意不参与 `reset_schema`**（审计要活过重置）→ 测试里断言"审计共 N 条"会跨用例、
  **甚至跨两次 pytest 运行**累积，第二次跑就红。正确姿势：按 `thread_id` 定位 + 断言增量 + 看末行内容。
- **"近 7 天"写成 8 天**：`created_at >= now() - interval '7 days'` 含边界日，返回 8 个自然日，
  前端按 7 根柱子画就对不上账。要用 `interval '6 days'`，并写一条"第 7 天前的单不能进窗"的回归用例。
- **JSX 括号里不能放多个兄弟元素**：`{cond && ( <div/> <div/> )}` → esbuild
  `Expected ")" but found "className"`，必须包一层 Fragment。
- **列表 key 不能用 Fragment 简写**：`<>` 不能带 key → React "unique key" 警告 + 展开行复用错位，
  要 `import { Fragment }` 用 `<Fragment key={...}>`。
- **"带着筛选跳转"要重新挂载**：已在该页面时再点另一条筛选，props 变化**不会**重置组件内部 state，
  用递增 `navSeq` 当 `key` 强制重挂载。
- **状态机拒绝动作也必须拒绝副作用**：被拒的流转绝不能改库、也不能写审计 ——
  "返回 400 但数据已经变了"是最危险的假成功（用例专门断言这一点）。
- **非 ASCII 查询参数**：手拼 `?status=已付款` → `UnicodeEncodeError`，一律 `urlencode(params)`。

## 跨租户越权（IDOR）（2026-09）踩过的坑

- **身份只写在提示词里 = 没有身份**：`ORDER_AGENT_PROMPT` 里"customer_id 必须填系统提供的值"
  是建议不是约束。三处工具调度点都是 `mcp.call_tool(name, args)` —— LLM 给的参数原样透传，
  于是普通客户能查别人的订单 PII、能在别人订单上建退款工单（并把订单推进「退款中」）。
  **凡是由模型提供的"身份/权限"参数，服务端都必须覆盖，不能信任也不会被提示词约束。**
- **`setdefault` 补参数 = 让不可信来源赢**：审批兜底写的是
  `args.setdefault("customer_id", 可信值)`，意图是"LLM 漏传时补齐"，
  实际是"LLM 传了就保留"。补安全默认值一律用**赋值**，不要用 `setdefault`。
- **授权要做两层，而且第 1 层是"覆盖"不是"合并"**：工具侧按 `order_no + customer_id` 查询
  （缺身份 fail-closed，且"不存在"与"不属于你"同一句话，不泄露存在性）；
  调用侧用服务端身份覆盖同名参数。只做工具侧 → `caller_id` 本身可被伪造；
  只做调用侧 → 新增调用点忘了注入就静默开洞。
- **越权写会"延迟发生"**：待审批表里存的 `args` 会被兜底路径直接拿去写单，
  所以**存进表的那一刻**就必须是可信身份，否则越权只是从"下单时"挪到"管理员点通过时"。
- **审计路由是查漏的好办法**：用 `inspect.signature` 遍历 `app.routes` 打印每个端点的
  依赖，一眼看出哪些接口没有 `Depends(get_current_user/require_admin)`。
  本次审计结果：业务接口全部有鉴权，公开的只有注册/登录/刷新/登出、`/healthz`、`/docs`。

## 退单联动（2026-09）踩过的坑

- **口径没定义清楚，用例会"碰巧通过"**：`refund_by_product` 的真值用**工单口径**，
  模型此前也用工单口径算，一直绿；退单联动上线、语义层写明"退款率 = 已退款订单/订单数"后，
  模型按新口径算，两者差 2.25 倍，用例立刻红。**这不是模型变差，是口径终于被写清楚了** ——
  正确处理是拆成两个名词 + 两条成对用例，而不是改断言让它过。
- **不变量必须能被检查**：手工回滚 E2E 误操作时，我把订单退回原状态、却让工单留在"待审核"，
  正好造出"客户以为在退款、系统里没任何标记"—— 就是这次要消灭的那种不一致。
  于是把"有未决工单 ⇒ 订单退款中"写成 `check_refund_invariants()`，回填脚本与测试共用。
- **"只能由 X 决定"的判断必须在状态机之前**：`退款中 → 已退款` 本来就在合法边里
  （审核走的就是这条语义），先判状态机会让管理端用同一个接口绕过工单直接改订单状态。
- **跨两张表的写入要同事务**：工单插入与订单状态变更拆成两个事务，中途失败会留下
  "工单成了、订单没动"（老问题重演）或"订单在退款中却没有工单可审"（订单被永久冻结）。
- **幂等 DDL 的替换要断言**：给 `refunds` 补 `order_status_before` 的 ALTER 因缩进不匹配
  静默没写进去，`orders` 的却生效了 —— 同一批修改**一半成功一半失败**，只有跑起来才暴露
  （`column r.order_status_before does not exist`）。每次替换后 `assert s != b` 之外，
  还要**核对该改的那一行真的在**。
- **回滚要回到"自洽状态"，不是回到"字段原值"**：误批退款后我把订单改回退款前状态，
  但工单已回到待审核 —— 单看每个字段都"恢复了"，组合起来却是非法状态。
  回滚的正确标准是**满足不变量**，不是每个字段各自复原。

## 数据完整性 / 外键化（2026-09）踩过的坑

| # | 坑 | 表现 | 教训 |
|---|---|---|---|
| 1 | **加外键不只是"清数据"** | 你以为洗完历史数据就能加，实际代码还在**持续产生**没有父行的数据（guest 兜底、/dev/login 的 mock、演示账号）—— 实测 63 个 user_id | 加约束前先立**不变式**（所有被接受的身份都要有账号行，影子账号兜底），否则清完明天又脏 |
| 2 | **外键加过头** | 我给 `conversations.session_id` 也加了外键，结果和既有设计打架：`default` 是**跨用户的历史遗留桶**，本来就不在 sessions 表里 | 外键要编码**真实不变式**，不是我们希望的不变式；加之前先读一遍设计文档 |
| 3 | **幂等检查漏了"存在但未校验"** | `if constraint exists: continue` → 清完孤儿后 `VALIDATE` 永远不执行，外键一直挂着 `NOT VALID` | 幂等判断要看清**状态**（convalidated），不能只看"存在与否" |
| 4 | **进程内缓存与"世界被重置"不同步** | 影子账号缓存跨测试存活，而 `reset_schema()` 把 users 表删了 → 缓存说存在、库里没有 → 撞外键 | 任何"存在性缓存"都要有显式的失效入口（`reset_user_cache()`），并在 schema 重建时调用 |
| 5 | **反编造检查冤枉"推算出来的数字"** | 结论写"结果共 84 行，未展示 72 行"（84-12）被判成编造 | 判定要允许**简单推算**（加减乘除 + 百分比形态），否则告警失真、管理员就不看了 |
| 6 | **测试里图省事插孤儿行** | 4 条原有测试直接插订单/对话而不建父行，加约束后集体失败 | 这是好事：测试被迫按真实语义写（先建父行）。**约束会顺带提升测试质量** |
| 7 | **中文字符串里嵌双引号**（第三次同类手误） | `print("已加入"可推算数字"白名单")` → SyntaxError，而 Python 先解析后执行，**整个脚本一行都没跑**（却以为改好了） | 改代码的脚本里，字符串一律用单引号或不用引号；改完立刻 `py_compile` + 断言 |
