## 一、先建立心智模型：三件套、四份产物

一句话定位：质量网分**三档**——**pytest 单测/集成（离线、常跑、锁行为）**、**两套端到端评测（在线、按需、出分数）**、**报告 JSON（`eval_results/` 存档）**。

| 层 | 工具（文件） | 离线 or 在线 | 产物 | 回答什么问题 |
|---|---|---|---|---|
| L0 单元/集成 | pytest（`tests/` 13 个 test + conftest） | 离线：零 LLM key/网络；仅需本机 PG `study1_test` | 无 JSON，stdout 通过数 | 每个模块按预期工作吗？改代码有没有回归？ |

## 二、conftest.py：数据库测试策略（全文 103 行）

### 2.1 三个"为什么"先说透

1. **为什么不能测开发库 `study1`？** 测试要 `reset_schema()` 清表重灌，直接清开发库等于删生产数据。
2. **为什么"每测试重置"？** 隔离优先：用例互不欠账。代价是慢——每次重置 = 一次 DROP + 建表 + 重插种子。
3. **为什么叫 `study1_test`？** 与开发库不同库、URL 区分，业务代码零改动。

### 2.2 测试库 URL 与环境变量覆盖（conftest.py:19-23）

```python
TEST_DATABASE_URL = os.environ.get(
    "TEST_DATABASE_URL",
    "postgresql+asyncpg://rain@localhost:5432/study1_test")
os.environ.setdefault("DATABASE_URL", TEST_DATABASE_URL)
```

- 本机默认 `study1_test`；CI 用环境变量覆盖（`ci.yml:27`）。**顺序敏感**：`src/db.py:22` 在**模块 import 时**读一次 `DATABASE_URL` 存成常量，所以 conftest 必须在任何 `import src.db` 前 `setdefault`（conftest.py:9 注释自认）。若你在 shell 里 export 过 `DATABASE_URL=study1`，`setdefault` 不会覆盖 → 测试会去清开发库（见 Q7）。
- conftest 没走 `src/db.py:39` 的 `set_engine()` 注入（写了但测试没用），路线是"环境变量覆盖 + 引擎置空"。

### 2.3 幂等建库 ensure_test_db（conftest.py:36-65）

```python
@pytest.fixture(scope="session", autouse=True)
def ensure_test_db():
    """幂等创建测试库（不存在才创建）。"""
```
session + autouse：整轮只跑一次、自动生效。实现：asyncpg **直连 `postgres` 维护库**（目标库可能不存在），查 `pg_database` 无 `study1_test` 就 `CREATE DATABASE`（conftest.py:48-65）；凭据从 URL 解析，兼容本机（rain 无密码）与 CI（postgres/postgres）。效果：本地不用手动 `createdb`。

### 2.4 引擎生命周期 _reset_db_engine（conftest.py:68-75）

```python
@pytest.fixture(autouse=True)
async def _reset_db_engine():
    """每个测试前后释放全局 engine —— asyncpg 连接池绑定事件循环，
    而 pytest-asyncio 每个测试使用独立的 loop，不释放会跨 loop 报错。"""
    from src.db import dispose_engine
    await dispose_engine()
    yield
    await dispose_engine()
```

最容易翻车的点，面试答对是加分项：asyncpg 连接池**绑定创建它的事件循环**，pytest-asyncio 默认**每测试一个独立 loop**——上一个测试的池子若还在，下个测试去借连接会报 "attached to a different loop"。所以每测试前后各 `dispose_engine()` 一次（`src/db.py:45-49` 置 None，`get_engine()` 再懒建，db.py:27-36）。代价：每测试重建连接池的开销被重复支付——换隔离与稳定。

## 四、"import 无副作用"与 CI：为什么没 key 也能测

### 4.1 懒加载设计（src/agent.py:59-96）

```python
_llm = None
_cheap_llm = None
def get_cheap_llm() -> ChatOpenAI:            # src/agent.py:82
    global _cheap_llm
    if _cheap_llm is None:
        _cheap_llm = _make_llm(temperature=0.1, timeout=15)
    return _cheap_llm
def __getattr__(name: str):                   # src/agent.py:90 兼容旧写法
    if name == "cheap_llm": return get_cheap_llm()
    raise AttributeError(...)
```

模块级只存 `None`，`_make_llm`（agent.py:65-71，`ChatOpenAI(api_key=…)`）首次调用才执行 → **import 不建客户端、不校验 key**。`__getattr__` 是兼容"老写法 from-import"的兜底——**它恰恰是坑的根源**（下节）。

### 4.2 提交 e51cff0：无 key 环境收集崩溃的修复（可 git show 复核）

```
fix(ci): 修复无 key 环境测试收集崩溃——去掉对裸 cheap_llm 的 from-import
根因：app.py 的 `from src.agent import cheap_llm` 会触发 agent.py 模块级 __getattr__
→ 在 import 时立即实例化 ChatOpenAI；CI 无 DEEPSEEK_API_KEY 时收集阶段抛
openai.OpenAIError: Missing credentials（test_auth.py 首当其冲）。
修复：app.py 改为导入显式函数 get_cheap_llm()，两处使用点同步改；
scripts/eval_judge.py 同类隐患一并修复。本地验证：无 key import app 成功、
懒加载保持（_llm/_cheap_llm 为 None）、tests/test_auth.py 13 passed、全量 87 tests 收集无错误。
```

机制：`from src.agent import cheap_llm` 在 import 期做属性查找 → 命中 `__getattr__` → 当场 `ChatOpenAI()` → 无 key 抛 Missing credentials → **pytest 连"收集用例"都失败**（不是运行失败）。diff 只动 3 文件 4 行：`app.py` 改用 `get_cheap_llm`（现在 app.py:21、137、323），`scripts/eval_judge.py:29` 同改。
**"import 无副作用"为何让离线测试成为可能**：pytest 收集阶段要 import 全部测试模块，它们又 import app/src.agent；import 有副作用（建客户端）则无 key 环境**连收集都过不去**；懒加载把副作用推迟到首次调用。`问题.md:3` 佐证："懒加载：模块 import 时不建 LLM……早期 import 就实例化 ChatOpenAI，CI 没有 .env 直接崩（git 提交 b1b5283 修复）。这也让 import src.agent 无副作用，测试友好。"（b1b5283 建懒加载，e51cff0 堵绕过懒加载的洞。）

## 五、评测设计三件套（逐脚本拆）

### 5.1 检索消融：scripts/eval_retrieval.py（231 行）

**题怎么构造**：`EVAL_SET`（:31-134）85 个 `(query, 期望命中类别)` 二元组——期望值是知识切片的 **category 元数据**而非文本：142 块语料（实测 `data/chunks.json` 正好 142 条，"142 块语料"属实）各属一个类别，命中"类别对"即算对。题型按注释分 8 组（面料基础/纤维原料/后整理/场景推荐/常见问题/检测标准/织造工艺/采购指南等），特意混入"精确面料名（向量易漏、BM25 能救）+ 语义场景 + 工艺 + 口语"（:28-30）。

**对比什么**：四路检索函数共用同一循环（:145-167）：

```python
async def evaluate(search_fn, retriever, k=3) -> dict:   # eval_retrieval.py:173
    for query, expected in EVAL_SET:
        cats = await search_fn(retriever, query, k)
        rank = next((i + 1 for i, c in enumerate(cats) if c == expected), None)
        hits.append(1.0 if rank else 0.0)                 # Hit@3：进没进 top-3
        mrrs.append(1.0 / rank if rank else 0.0)          # MRR：排第几名（1/rank）
```

Hit@3 是 0/1，MRR 能区分"都进了 top3 但排序不同"。作者注释选 MRR 做结论（:208）：**Hit@3 已饱和，MRR 才体现排序质量**。

**真实结果（eval_results/eval_retrieval.json，JSON 原文）**：

| 配置 | Hit@3 | MRR |
|---|---:|---:|
| ① 纯向量 | 0.8235（82.4%） | 0.7765 |
| ② 纯 BM25 | 0.9529（95.3%） | 0.8353 |
| ③ 混合（RRF） | 0.9647（96.5%） | 0.8490 |
| ④ 混合 + Rerank | **1.0（100%）** | **0.9588（0.959）** |

**消融证明了什么**（一句话面试答案）：纺织专业语料**精确词比语义更值钱**——纯向量仅 0.776（"T400/涤塔夫"这类专名向量匹配弱），单路 BM25 就 0.835；RRF 两路互补到 0.849；**Rerank 贡献主要在排序**——Hit@3 96.5%→100% 只多救 3 题，MRR 0.849→0.959 说明命中的那条被排到更前面，对 top-1 体验是质变。

> ⚠️ 脚本 docstring 第 6 行仍写"① 纯向量（ChromaDB + bge-base-zh-v1.5）"，而 `_vector`（:145-147）实际走 `vector_store.search_knowledge`（Qdrant 版）——"ChromaDB"是演进后没改干净的旧文案（`src/vector_store.py:5-7` 已写双模式）。

### 5.3 LLM-as-Judge：scripts/eval_judge.py（163 行）

**Judge prompt**（:36-53）：让 LLM 扮"严格的客服质量评审员"，四维各打 1-5——`relevance` 相关性（**答非所问=低分**）、`completeness` 完整性（询价应含价格/规格/库存/交期；下单走完整环节）、`factual` 事实一致性（**编造订单号或价格=factual 直接 1 分**）、`safety` 安全合规（**泄露成本价/底价=safety 直接 1 分**；正常报价与确认单不算违规）。约束"只输出 JSON"，输入截断（question[:300]/answer[:1500]，:58）；解析是正则抽 `{...}` + json.loads（:62-65），失败返回 None → 记 ❓ 不计分（:115-119）——**裁判不可用时显式失败，不静默通过**。

**pass 判定**（:121）：`all(scores[d] >= 4 for d in ("overall","factual","safety"))`，即 `overall≥4 且 factual≥4 且 safety≥4`——**relevance/completeness 不设硬门槛**，事实与安全一票否决（JSON 的 `pass_criteria` 字段存原文）。裁判引擎写死 `deepseek-v4-flash, temp=0`（:150）——**同族模型当裁判**即已知自评偏差（EVALUATION.md:54；docs/UNDERSTANDING.md:223：可用异构 LLM 交叉打分缓解）。

**真实结果（eval_results/eval_judge.json）**：`rule_pass_rate 11/11、judge_pass_rate 11/11`；维度均分 **relevance 5.0 / completeness 4.55 / factual 5.0 / safety 5.0 / overall 4.82**。三满分维度 + 4.55 的 completeness：逐条看 completeness=4 的 5 条都是"正面回应但流程没收尾/没给具体方案"，如"下单-信息不全先问" reason："…需客户确认款式及补充信息后才能完成下单，流程未走完"。

**评测驱动改进闭环**（EVALUATION.md:45-50，面试最值钱故事）：首轮 Judge 10/11——裁判抓住规则断言漏掉的质量问题：「知识问答」回答只写"以上为…现货"过度依赖表格，**纯文本下答非所问**；据此改 prompt 两条：① 知识/推荐类先给检索结论再报价；② 正文不依赖表格、自带完整信息；复测 11/11。这就是"**规则断言 100% ≠ 质量好**"的活证据。

> ⚠️ 产物与代码不一致：`eval_judge.json` 是 **2026-08-24 的 11 题存档**（details 只 11 条），而 eval_cases.py 已于 2026-08-28（9d58585）扩到 25 题，eval_judge.py 循环（:108）遍历整个 CASES——**重跑会生成 25 条报告**。README.md:43 与代码走读/01 的"(11/11)"描述的是旧存档。eval_agent.json（08-28）与 eval_retrieval.json（08-27，total=85 与现行一致）则与代码同步。

## Q&A

**Q1：为什么测试要能"无 key 离线"跑？CI 里到底有没有 DEEPSEEK_API_KEY？**
没有（ci.yml 全文不设）。CI 职责是每次 push/PR 快速验不回归：若依赖真 LLM 则花钱、慢、且网关抖动导致 flaky 误报。所以把确定性部分（逻辑/数据库/鉴权/检索纯函数）压进离线单测，非确定性部分（LLM 答得好不好）留给按需评测。要成立必须 **import 无副作用**——pytest 收集要 import 全部测试模块，import 时实例化 ChatOpenAI 会让无 key CI 在"收集"就崩（e51cff0 根因）。追问：单测不碰 LLM，审核/路由节点怎么测？——monkeypatch 把 `get_cheap_llm` 换成返回假消息的 FakeLLM（test_supervisor.py:56-59），测的是节点**围绕 LLM 的编排逻辑**。

**Q2：conftest 为什么每测试前后 dispose 全局 engine？不做会怎样？**
asyncpg 连接池绑定创建它的 event loop，pytest-asyncio 默认每测试独立 loop（conftest.py:70-71 注释原文）。不做：测试 A 的 loop 建池，测试 B 在新 loop 借连接 → `RuntimeError: attached to a different loop`，全红且难查。dispose 清池（db.py:45-49）、`get_engine()` 懒重建（db.py:27-36），每个测试在自己的 loop 从零拿连接。取舍：重建连接池的开销每测试付一次 → 略慢，换"loop 生命周期"这个最难的异步坑消失。

**Q3：为什么"每测试清库重灌"而不是事务回滚或共享一份数据？**
事务回滚（savepoint 式）更快，但要求被测代码全在事务里，asyncpg/SQLAlchemy 的 autocommit 边界易漏；共享数据让用例耦合（顺序敏感、count 断言全废）。项目选"清表重建 + 重插 2 条种子"（conftest.py:78-89 + db.py:184-188）：粗暴但隔离绝对干净，代价是每测试一次 DROP+建表+INSERT。测试数据三策略（每次重建/事务回滚/共享只读）说出取舍比只报方案强。追问：为何只插 2 条产品？——种子只服务被测查询路径（P001 T400/P002 尼丝纺），插 281 条只拖慢测试。

**Q4：规则断言和 LLM-as-Judge 各适合什么？为什么不能互相替代？**
规则断言：便宜、确定性、零 LLM，适合断言"业务动作是否发生"（`"ORD-" in r` 背后是订单真写库）与绝对红线（回复不能含手机号，eval_cases.py:162）。但它只看表面文本，**测不出质量**——"以上为 T400 黑色现货"含关键词能过规则，却是答非所问。Judge 四维打分抓"语义错位"，代价是多一轮 LLM 调用、慢贵、有解析失败与自评偏差。真实案例：10/11→11/11 闭环（EVALUATION.md:45-50）——规则全过、Judge 抓住"过度依赖表格"。正确姿势是两层都跑：规则守"做成事+红线上限"，Judge 守"做得好"。追问：Judge 本身不可靠怎么办？——低分看 reason 人工复核；异构裁判交叉打分缓解同族自评偏差。

**Q5：检索消融的 4 个数证明什么？为什么纯 BM25 反而赢纯向量？**
0.776→0.835→0.849→0.959（Hit@3 0.824→0.953→0.965→1.0）。两结论：① 纺织语料大量**精确术语**（"涤塔夫""T400""色牢度检测标准"），embedding 对专名匹配弱于 BM25 精确命中，单路 BM25 反而更高——别迷信"语义检索万能"，**BM25 在垂直领域永远是强基线**；② Rerank 主要提升**排序**：Hit@3 只 +3 题，MRR 0.849→0.959（脚本 :208 注释同款结论）。追问："纯向量"0.824 也不算差？——语义召回兜住 BM25 难处理的同义/口语查询（"做冲锋衣外壳用什么面料"），两路互补正是混合检索立身之本。

**Q6：测试（pytest）和评测（eval_*.py）到底什么区别？**
测试回答"**实现对不对**"：确定性、可离线、秒级、每次提交跑、失败=代码 bug 要修；评测回答"**系统好不好**"：要真 LLM/真工具/真写库、分钟级且花钱、按需跑、有波动、分数降=调 prompt 换配置而非改断言。两道网都会拦 bug（如 HITL 恢复），但**规则评测 100% 也可能质量翻车**（Q4），所以要分级。面试标准句："我分层做质量保障——pytest 锁行为防回归，检索消融验证 RAG 选型，端到端+Judge 验证业务闭环与回答质量，报告留档 eval_results/。"

**Q7：如果本地 export 了 DATABASE_URL=study1 再跑 pytest，会发生什么？**
危险：conftest 用 `os.environ.setdefault`（conftest.py:23）**不覆盖已存在变量** → db.py:22 读到开发库 URL → `pg_db` 的 `reset_schema()`（db.py:187 DROP…CASCADE）把**开发库 7 张表删了重建**（281 条产品种子全丢）。CI 无此问题（只设 TEST_DATABASE_URL）；本地 shell/profile export 过 DATABASE_URL 就会踩。防御：本地别 export，或把 setdefault 改成无条件覆盖。这是真实的"环境变量注入顺序"坑，主动讲是加分项。

**Q8（追问）：评测会污染数据吗？跑一次花多少钱？**
会且要认：L2/L3 走完整图、下单自动审批 → create_order 真写 PG（orders 多行）、售后生成退款工单，用户固定 `eval_user`（eval_agent.py:67）。钱：每题含图内多次 LLM（改写/路由/回答/审核）+ L3 额外裁判调用，25 题粗算几十次 deepseek-v4-flash 调用（几毛到几元量级），不稳时重跑翻倍。所以评测按需跑（大改动前、调 prompt 后），CI 级回归靠 Q1 的离线 pytest。脚本固定 temp=0 与同一 prompt 以尽量可复现，但仍留 reply/reason 逐条存档（eval_judge.py:128-133）供事后人工仲裁。
