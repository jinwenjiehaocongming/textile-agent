# 09 · 售后流程 · 查单、退货规则与退款工单

> 目标：看懂客户说"我要退货"之后，售后 Agent 怎么查订单、怎么对照退货规则下结论、
> 以及"退款工单"到底写进了哪张表、之后还有没有下文。
> 覆盖 after_sales_agent.py、refund_server.py（query_order / create_refund）、orders/refunds 表。
> 顺带点破两个诚实边界：工具层没有 customer_id 归属校验；退款状态停在"待审核"没有推进端点。

---

## 一、先建立心智模型：售后是"已有订单"的下游

| | 下单流程（08 步） | 售后流程（本步） |
|---|---|---|
| 前提 | 从零创建一条订单 | **订单必须先存在**（客户报订单号 → 查库） |
| 数据库动作 | INSERT orders（状态 待付款） | 查 orders + INSERT refunds（状态 待审核） |
| 有没有审批 | 有：interrupt 挂起人工审批（HITL） | **没有**：规则对照后直接生成工单 |
| 终态 | 订单号生成 | 工单生成即止，后续靠线下人工 |

| 角色 | 文件 | 干什么 |
|---|---|---|
| Supervisor | `src/agent.py` supervisor_node | 把"退货/退款/投诉/催货"路由到售后 Agent |
| 售后 Agent | `src/after_sales_agent.py` | 提示词写死退货规则；绑工具循环执行 |
| 售后工具 | `src/mcp_servers/refund_server.py` | `query_order` 查订单、`create_refund` 写工单 |
| 存储 | `src/db.py` refunds 表 | 工单：order_no + reason + status='待审核' |

一句话：**售后 = 用"订单号"这把钥匙打开订单，对照规则判断责任，然后落一张待人工审核的
退款工单**。类比：线下退货——你拿着小票（订单号）到柜台，店员查系统（query_order）、
对照退货政策（提示词里的规则）判断给不给退，能退就开一张"退货单"（create_refund），
后续退钱是财务的事，跟这个柜台没关系了。

## 二、Supervisor 怎么路由到售后

主 supervisor 的 LLM 提示词（agent.py:376-385）把意图分成三类：

```
- sales: 询价、推荐、知识、闲聊、打招呼、查订单
- order: 明确要下单（"确认下单""帮我安排""就要这个"）
- after_sales: 明确要退货、退款、投诉、催货
```

分类结果经 agent.py:462 映射成 `query_type`（`after_sales` → `"after_sales"`），
`supervisor_router`（agent.py:503-509）据此路由到 `after_sales_agent` 节点。进入售后后的
多轮延续没有下单那样的专属 Layer 0.5/0.6，靠通用规则延续层（`_detect_continuation`，
agent.py:353-373：上一轮 AI 在提问"？"且客户回了个短句 → 沿用上一轮的 query_type）。

**一个诚实的发现**：after_sales_agent.py:54-59 定义了一个关键词路由函数
`should_after_sales`（退货/退款/色差/催发货……），但全项目**没有任何调用点**——
图路由实际走的是上面 LLM 分类 + query_type 延续，这个函数是遗留死代码。
面试可以主动说："这文件里有个没用上的关键词路由，说明演进过程中路由职责从关键词函数
迁移到了 Supervisor 的 LLM 分类，函数没删干净"——比假装没看见强。

售后节点完成信号（agent.py:494-500）：回复里含"退款工单已生成"就把 query_type 重置回
chat（与下单的 order_completed 同理，防止下一句又被续到售后）。

## 三、售后 Agent：提示词即"退货规则书"

AFTER_SALES_PROMPT（after_sales_agent.py:65-102）规定的流程：先问订单号 → 查到后确认
问题 → **对照退货规则** → 属我方责任就建工单。核心规则逐字摘录（after_sales_agent.py:78-86）：

| 方向 | 规则（原文） | 行号 |
|---|---|---|
| 可退 | 纬斜率超过 3% 可退货 | after_sales_agent.py:78 |
| 可退 | 色差超合同约定等级（缸差超半级）可退货 | :79 |
| 可退 | 破洞、油污、勾丝等明显疵点超四分制标准可退货 | :80 |
| 不可退 | 已裁剪加工不可退货 | :81 |
| 不可退 | 定制染色不可退货 | :82 |
| 不可退 | 已确认产前样、大货一致不可退货 | :83 |
| 验收 | 超 30 天未提出异议视为验收合格 | :84 |
| 验收 | 大货到货建议 7 天内验收 | :85 |
| 物流 | 物流破损由物流公司赔付，我方协助处理 | :86 |

配套的"投诉处理规范"（:88-94）：先共情道歉、再落实具体问题、对照规则、给具体下一步；
原则里还有两条红线：**不确定就建议寄回样片检测**、**不直接承诺赔多少钱——"工单审核后由
人工确认"**（:99-100）——钱的口子留给人工，Agent 不越权承诺。

执行节点 `after_sales_node`（after_sales_agent.py:105-151）与下单 Agent 同构：绑
**只有** `query_order` + `create_refund` 两个工具（:109-111）——不绑产品库、不绑
create_order，**售后 Agent 物理上没有报价/下单的能力**（最小权限：只发"我要干售后"的
证，拿不到别的门的钥匙）。循环里最多 5 轮 ReAct（:125），且一旦本轮调用了
`create_refund`，直接返回工具结果那条消息（:145-147）：

```python
if any(tc["name"] == "create_refund" for tc in response.tool_calls):
    tool_msg = tool_msgs[-1]
    return attach_render_data(tool_msg, find_render_data_in_msgs(conversation))
```

注意：**工单生成后不让 LLM 再复述一遍**（复述 = 二次编造的机会），把
"✅ 退款工单已生成！订单号：……"原样作为最终回复返回（挂上表格渲染数据给前端）。

## 四、工具侧：refund_server.py 的两个工具

### 4.1 query_order —— 售后版查单（refund_server.py:15-28）

```python
@mcp.tool()
async def query_order(order_no: str) -> str:
    """查询订单详情（售后用，比 order_server 的版本多了地址电话）。"""
    row = await query_one("SELECT * FROM orders WHERE order_no = :order_no", {"order_no": order_no})
```

- 参数**只有 order_no**，返回整行订单含**电话 + 地址**（注释自述：比 order_server 的
  `query_order_status` 多地址电话——查单工具其实有两个近似副本，见 Q6）。
- 订单归属校验？**工具层没有**：不传 customer_id、SQL 里没有 `WHERE customer_id`。
  只要知道订单号，任何会话都能查回订单的收货人电话地址（诚实边界，Q2 展开）。
- `SELECT *` 全列拉回，代码里只挑字段拼文本（:22-27），属于演示期偷懒写法。

### 4.2 create_refund —— 写退款工单（refund_server.py:31-48）

```python
await execute(
    "INSERT INTO refunds (order_no, reason, status, created_at) VALUES (:order_no, :reason, '待审核', :created_at)",
    {"order_no": order_no, "reason": reason, "created_at": now.isoformat()},
)
```

成功文案（:42-48）：

```
✅ 退款工单已生成！
订单号：ORD-...
退款原因：{reason}
状态：待审核
我们的售后人员将在 1 个工作日内审核并联系您。
```

**如实记录三个边界**（代码可证）：
1. `create_refund` 不校验 `order_no` 在 orders 里是否存在（纯 INSERT，refunds 表也没有
   外键）——对着一个编造的订单号也能生成工单；
2. 不校验归属（同上，无 customer_id）；
3. refunds 的 reason 是**客户/LLM 自由文本**，退款金额无从谈起——工单只是"记录了一个
   诉求"，不是真实的退款单（没有金额字段、没有退款执行）。

## 五、refunds 表与状态流转：演示只到"工单生成"

refunds 表（db.py:113-119）：

```sql
id         SERIAL PRIMARY KEY,
order_no   TEXT NOT NULL,
reason     TEXT NOT NULL,
status     TEXT DEFAULT '待审核',
created_at TEXT NOT NULL
```

状态字段默认 `'待审核'`。**有没有把它推进到"已审核/已退款"的代码？搜遍全项目：没有。**
没有任何 `UPDATE refunds`（同样也没有 `UPDATE orders`——08 步提过 orders 停在"待付款"）。
所以：

| 环节 | 代码里有吗 |
|---|---|
| 生成工单（INSERT refunds, status='待审核'） | ✅ refund_server.py:37 |
| 工单列表给售后人员看 | ❌ 没有端点查 refunds 表 |
| 审核/驳回/退款状态推进 | ❌ 全项目无 UPDATE refunds |
| 金额核算 / 真正退款 | ❌ 无字段无逻辑 |

**对比下单流程**：下单有完整 HITL 闭环（挂起 → 管理员审批 → 写库 → 审计，08 步）；
售后是**半闭环**：规则判断 + 工单生成自动化了，审核那一步留给"1 个工作日内联系您"的
线下人工。这是演示系统的边界，面试答"售后服务停在工单生成、状态流转与审核端点是下一步
要补的（refunds 加 admin 端点 + status 推进 + 与 audit_log 联动）"是诚实的工程表达。

## 六、与下单流程的关系 & 归属隔离真相

### 6.1 为什么"先有订单"这条约束天然成立

售后要查的 order_no 从哪来？
1. 客户主动报（提示词第一步就是"客户没提供订单号 → 问他要"，after_sales_agent.py:69）；
2. 历史对话里有（下单成功时 create_order 返回过真实订单号，render 工具会展示，08 步）。

而且**售后 Agent 提示词里没有"查不到就说查到了"的空间**——`query_order` 查不到返回
"未找到订单 {order_no}"（refund_server.py:19-20），LLM 只能照实转述；主 Agent 提示词里
同样有【查单红线】（agent.py:254-256）：只能展示工具返回的真实订单，**严禁自己编造订单号
或订单卡片**——因为"你拼出的任何 ORD- 开头订单号都不是真实订单"。

### 6.2 行级隔离的真相：隔离在 HTTP 层，不在工具层（2026-09 已修复）

**当时的诊断（保留原文，这是本次修复的起点）**：

> 这个系统里真实存在的行级隔离是 conversations/profile/sessions（按 `user_id` 过滤）
> 和 `/orders` HTTP 端点（`WHERE customer_id = :uid`）；
> 而 MCP 工具层（query_order / query_order_status / create_refund）是**无调用者身份**的：
> 工具签名里压根没带 user_id，售后节点调用时也没传。
> 后果：**知道订单号就能查任何人的订单、给任何订单号开工单** ——
> 靠的是订单号不可猜（ORD- 带微秒+随机）+ 客户只能从自己的历史里拿到真实单号。
> 这是典型的**演示级安全模型**（"防不知道、不防知道"），不是生产级。

**这个洞是真的，而且可以复现**（2026-09 实测，普通客户账号即可）：

| 攻击 | 改之前的结果 |
|---|---|
| 让 Agent「查一下订单 ORD-别人的单号」 | `refund_server.query_order` 返回**别人的电话与地址** |
| 让 Agent「退掉订单 ORD-别人的单号」 | 工单建在别人的单上，且订单被推进「退款中」（**跨租户写**） |
| 提示词注入让下单带上别人的 `customer_id` | 订单**记在别人名下**，而且延迟到管理员审批通过时才发生 |

第三条尤其说明问题的性质：`ORDER_AGENT_PROMPT` 里那句"customer_id 必须填系统提供的值"
是**提示词建议，不是约束**；而 `app.py` 的审批兜底路径写的是
`args.setdefault("customer_id", 可信值)` —— 本意是"LLM 漏传时补齐"，
实际效果是"**LLM 传了就保留**"，攻击者填的值反而赢。

**修法：两层，缺一不可**（`src/order_access.py`）

1. **服务端强制注入身份**：三处工具调度点
   （`order_agent` / `after_sales_agent` / `agent.tool_executor`）都不再
   `call_tool(name, args)` 直通，而是 `call_tool(name, with_trusted_identity(name, args, 可信身份))`。
   注入用**同名键覆盖**（不是 `setdefault`）：LLM（或攻击者）塞进来的 `caller_id` /
   `customer_id` 一定被冲掉。
2. **工具侧按归属查询**：`order_no + customer_id` 一起查，缺 `caller_id` 直接
   **fail-closed 拒绝**；"查不到"与"不属于你"返回**同一句话**，不泄露订单是否存在。

> 为什么必须两层：只做第 1 层，将来新增调用点忘了注入就静默开洞；
> 只做第 2 层，`caller_id` 本身来自 LLM args，攻击者把它填成受害者的 id 就能绕过。
> 这也是 `tests/test_cross_tenant_access.py` 里"注入必须被覆盖"那条用例存在的理由。

**顺带统一的边界**：`create_order` 的身份同样由服务端覆盖（`IDENTITY_TOOLS`）；
写进 `pending_approvals.args` 的那份参数也必须已经是可信身份 —— 否则越权不会消失，
只是从"下单时"推迟到"管理员点通过时"发生，更难追查。

**验证**（走真实 MCP 子进程通道，不是进程内调用）：

```
[① 越权读]        未找到该订单，或该订单不属于您   → 电话/地址均未泄露
[② 越权写]        同上（拒绝）                   → 受害者订单 已发货 → 已发货（未被改动）
[③ 伪造 caller_id] 同上（被服务端覆盖后拒绝）      → 未泄露
[④ 本人查询]       正常返回（含电话地址）
```

## 七、一条售后对话的完整旅程（数据视角）

```
客户："ORD-20260901-... 这批货纬斜很严重，要退货"
  → Supervisor LLM 分类 after_sales（agent.py:376-385）
  → after_sales_agent 节点：LLM 调 query_order(order_no)
      → SELECT * FROM orders WHERE order_no=...（refund_server.py:18）
      → 返回订单详情（含纬斜判断需要的状态/数量）
  → LLM 对照提示词规则："纬斜率超过3%可退货"（after_sales_agent.py:78）
  → LLM 调 create_refund(order_no, reason)
      → INSERT refunds(... '待审核')（refund_server.py:37）
      → 返回 "✅ 退款工单已生成！..."
  → after_sales 节点直接返回该工具消息（after_sales_agent.py:145-147）
  → agent.py 检测 "退款工单已生成" → query_type 重置 chat（agent.py:498-499）
  → 文案经 review 审核（本消息是工具结果、非 AI 文本，审核跳过，agent.py:335-338）
```

## Q&A

**Q1：售后为什么也要"工具 + MCP"，而不是让 LLM 直接凭记忆编，或后端直连数据库？**
三个理由层层递进：
1. **防幻觉是硬约束**：售后回答建立在"这单真实存在、状态是什么"之上。query_order 查不到
   就返回"未找到订单"（refund_server.py:19-20），LLM 只能照实转述；如果让 LLM 自由发挥，
   它会编出订单号、金额、甚至"已退款"（主 Agent 提示词里的【查单红线】agent.py:254-256
   就是专门写给这种情况的——历史上真出过"复述/编造订单卡片"的事故，08 步 order_completed
   修复同源）。
2. **写库必须走受控通道**：工单要落 refunds 表、售后人员才能看到。工具 = 一段确定性的
   代码（SQL INSERT + 固定文案），LLM 只负责"决定调不调、传什么参"，决定权与执行权分离。
3. **MCP 进程隔离**：工具跑在独立子进程里（mcp_client.py:40-46 用 stdio_client 拉起
   refund_server.py），Agent 进程不持数据库凭据、不直接拼 SQL；工具按名路由、按 schema
   校验参数（FastMCP 内建）。这就是"能力最小化"：售后 Agent 只绑 query_order +
   create_refund（after_sales_agent.py:109-111），连报价工具都没有。

**Q2：查单归属校验怎么做？能查到别人的单吗？**
如实答：**工具层没有归属校验**。query_order 参数只有 order_no（refund_server.py:16），
SQL 是裸 `WHERE order_no = :order_no`；售后节点也不传 customer_id（agent.py:496）。
所以严格说，**只要知道订单号，就能查到那单的收货人电话地址**。这个系统真正的行级隔离
在别处：conversations 按 user_id+session 隔离（memory.py）、`/orders` 端点
`WHERE customer_id = :uid`（app.py:383）。安全模型 = "订单号不可猜（时间戳+微秒+随机）+ 
真实单号只出现在自己历史里"，即"防不知道、不防知道"。反观下单侧 create_order 是带
customer_id 参数并写进表的（order_server.py:36），两相对照，售后侧漏传调用者身份是演进
遗留的洞——生产修法：MCP 会话级授权 / 工具加 customer_id 参数并在 SQL 加
`AND customer_id=:uid`。主动承认这个洞 + 给出修法，比辩解强。

**Q3：退货规则为什么写在提示词里，不写成代码规则？**
现状：规则是 AFTER_SALES_PROMPT 的纯文字（after_sales_agent.py:78-86）。优点：改规则
只改文案、零发布；规则要配合对话语境（"你收到几天了？有没有裁剪？"）由 LLM 动态询问，
代码规则做不了这种追问。缺点（诚实）：**文字规则不是约束**——LLM 可能漏看某条、把"超
30 天"算错、把"疑似"说成"确定"。真正的生产形态通常是三层：① 代码/规则引擎做**硬判定**
（可退/不可退/需人工，可测试、可审计）；② LLM 只做软性的共情与追问；③ 拿不准一律转人工
——本演示用提示词方案是因为量级小且规则本身模糊（"超四分制标准"这种判定本来就需要人
看布），面试答出"提示词放规则 = 快但软，硬规则早晚要下沉到代码"即可。别忘了提示词里有
兜底：不确定就建议寄回样片检测（after_sales_agent.py:99），钱的事一律留给人工（:100）。

**Q4：create_refund 不校验订单存在，对着假订单号也能开工单，是不是 bug？**
是缺陷，且可证：refunds 表无外键（db.py:113-119）、INSERT 前无 SELECT 校验
（refund_server.py:36-39）。后果：脏工单占着售后人力、audit 无从追溯。演示期"没炸"靠的
是调用方（LLM）只会拿 query_order 查到的真实 order_no 去开单（提示词流程第一步就是先查
单）。生产必修：create_refund 先查 orders 存在 + 归属 + （最好）状态机（只有非终态订单可
退），再 INSERT。这个"工具自身不设防、靠调用方自觉"的 pattern 在整个工具层反复出现
（产品搜索没权限问题所以无感，查单/退单一碰钱和隐私就露馅）——值得当反面案例讲。

**Q5：为什么 create_refund 后直接把工具消息当回复，不让 LLM 润色一遍？**
after_sales_agent.py:145-147：一旦本轮调了 create_refund，立刻返回工具结果那条
ToolMessage（挂渲染数据），不再给 LLM 一次开口机会。原因与 08 步同源：**复述 = 篡改
机会**——LLM 复述工单号时可能改字、加戏、或把"待审核"说成"已退款"，而订单号/状态这类
事实性内容应以工具输出为准。代价（诚实）：少了 LLM 的安抚话术，回复是硬邦邦的模板——
这是"事实保真"与"语气圆润"之间的取舍，本项目选了前者（提示词里其实要求过"先共情再落实"
after_sales_agent.py:89-94，但那发生在**调工具前**的轮次里）。

**Q6：query_order 和 order_server 的 query_order_status 几乎重复，为什么有两份？**
refund_server.py:17 注释自认："比 order_server 的版本多了地址电话"。历史原因：主 Agent
绑 query_order_status（agent.py:280），售后要拿电话地址做线下联系，就复制了一份加了字段。
两份都 `SELECT * ... WHERE order_no`（refund_server.py:18 / order_server.py:22），将来
orders 表加列要同步改两处。诚实点评：这是"按需复制"式演进留下的重复代码，重构方向是
一个工具带 include_contact 参数或售后直接复用主查单工具 + 单独的联系方式工具。面试能
主动指出跨 server 的重复实现，说明你真读了代码。

**Q7：Supervisor 怎么区分"查一下我订单到哪了"（sales）和"退货"（after_sales）？**
看 supervisor 提示词：**查订单被归到 sales**（agent.py:377："sales: 询价、推荐、知识、
闲聊、打招呼、查订单"），只有"退货、退款、投诉、催货"才进 after_sales（agent.py:379）。
所以"物流/催发货"类问题其实踩在分界线上：主 Agent（sales）绑了 query_order_status 也能
查状态；售后提示词里也列了"物流/发货问题 → 查状态告知进度"（after_sales_agent.py:74）。
最终归谁由 LLM 按当前消息判断 + 历史 query_type 延续决定——这也是为什么售后文件里的
`should_after_sales` 关键词函数成了死代码：关键词时代"催发货"想进售后，迁移到 LLM 路由
后这类软分界交给模型，规则函数就没人调了（二节）。追问点：这种软分界会不会把"查单"误
路由进售后？会，但售后 Agent 只绑查单+开单工具、且规则提示词里查单也合法，误路由的代价
只是少一点报价能力，不会出安全事故——容错设计使然。
