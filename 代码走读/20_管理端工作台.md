# 20 · 管理端工作台（订单状态机 / 退款审核 / 角色分界面）

> 这一节补的是**后端原本一个都没有**的一类接口：管理员"管事"的能力。
> 在此之前，管理员能做的只有"审批下单"和"看用户列表" —— 想发货、想审退款、想看全站订单，
> **没有任何接口**。代码位置：`src/admin_orders.py`、`app.py`（5 个端点）、
> `web/src/components/{AdminDashboard,OrderManager,RefundPanel}.jsx`。

---

## 一、先看清"缺什么"：三张表躺着没人管

| 现象 | 证据（改之前实测） | 后果 |
|---|---|---|
| `refunds` 有 38 条工单，其中 11 条 `status='待审核'` | 全库 grep 没有任何接口读写 `refunds.status` | 退款 Agent 建的工单**永远躺在那儿**，客户等不到结果 |
| `orders.status` 是自由文本列 | 只有下单时写入初值，之后无人改 | "已发货/已收货"永远到不了，分析模块的**发货时效恒为空** |
| 管理员只有 `/orders`（我的订单） | 该接口 `WHERE customer_id = 当前用户` | 管理员看不到任何**别人的**订单，而管理员自己根本不下单 → 列表恒为空 |

一句话：**客户侧的闭环是完整的，管理侧的闭环是断的。** 这一节就是把断的那半段接上。

## 二、订单状态机：把"谁都能改"变成"只能按业务路径走"

`status` 是自由文本，如果直接 `UPDATE orders SET status = $1`，等于把一个**业务不变量**交给调用方。
所以状态机显式写死在代码里（`src/admin_orders.py`）：

```
待付款 ──付款──→ 已付款 ──发货──→ 已发货 ──收货──→ 已收货（终态）
   │                │
   └────取消────→ 已取消（终态）←────┘
```

四个刻意的设计：

1. **非法转换 400，不是静默接受**：跳步（待付款→已发货）、原地打转（已付款→已付款）、
   终态再改（已收货→已付款）全部拒绝，并把"当前可流转到哪些"写进错误信息 ——
   前端的按钮就是照这句话渲染的。
2. **拒绝必须不留痕**：用例专门断言"被拒的流转不能改到库里的 status"，也**不能写审计**。
   "返回 400 但数据已经改了"是状态机最危险的假成功。
3. **顺手补时间戳**：`已付款 → paid_at`、`已发货 → shipped_at`（TEXT ISO，与既有列一致，
   用 `coalesce(col, now)` 只补不覆盖）。不补的话，数据分析 Agent 的"付款/发货时效"永远是空值 ——
   状态机不只管合法性，还得让**下游指标有数据**。
4. **前端抄一份 ALLOWED_TRANSITIONS**：非法动作直接不显示按钮。但**前端不是防线** ——
   后端仍会校验（curl 一样能打），这点在代码注释里写明了，避免后人误以为"前端禁了就够了"。

## 三、退款审核：CAS 解决"两个管理员同时点"

`refunds` 补了三个列：`decided_at`（文本 ISO）、`decided_by`、`note`（原因/备注）。

改列时踩了一个**顺序坑**：我先在 `SCHEMA_SQL` 里写了

```sql
ALTER TABLE refunds ADD COLUMN IF NOT EXISTS decided_at TEXT;   -- ❌ 放错位置
...
CREATE TABLE IF NOT EXISTS refunds (...);
```

开发库因为 `refunds` 早就存在，ALTER 成功，一切正常；**测试库（空库）直接炸**：
`relation "refunds" does not exist`。正确做法是两件都做：

- 新列直接写进 `CREATE TABLE`（新库一次建好）；
- `ALTER ... IF NOT EXISTS` 放在 `CREATE TABLE` **之后**（老库补列）。

> 教训：**幂等 DDL 也有顺序语义**。"IF NOT EXISTS 就安全了"只覆盖了"列已存在"，
> 没覆盖"表还不存在"。判断标准很简单：**在空库上从零初始化一遍**。

审核只允许一次，靠的是 CAS 而不是"先查后写"：

```sql
UPDATE refunds SET status=..., decided_at=..., decided_by=..., note=...
 WHERE id=:i AND status='待审核' RETURNING id
```

`WHERE` 里的 `status='待审核'` 就是并发闸门：两个管理员同时点"通过"，
只有一个 `UPDATE` 能匹配到行，另一个拿到空结果 → 明确告诉用户"该工单刚被其他人处理过了"。
（先 `SELECT` 再 `UPDATE` 的写法在这里必然翻车：两个请求都可能读到 `待审核`。）

前端因此做了两件事：驳回**必须填理由**（客户会看到），以及审核失败后**重新拉列表** ——
"已被别人处理"的真相要立刻显示出来，而不是留一个过期的按钮。

## 四、管理端界面：不是"客户界面的缩小版"

用户的原话是"管理员不需要那种下单的 agent，只需要处理订单和数据分析"。
所以界面按**角色**分了两套，而不是把客户界面藏掉几个按钮：

| | 客户 | 管理员 |
|---|---|---|
| 侧栏 | 新建对话 + 会话列表 | **管理导航**（工作台/订单管理/退款审核/订单审批/用户管理/数据分析）+ 最底部"客户视角" |
| 默认落地页 | AI 客服对话 | **经营工作台** |
| 顶栏导航 | "我的订单" toggle | 无（导航在侧栏，6 个页面顶栏挤不下） |
| 主视图 | 聊天 / 我的订单 | 工作台（指标 + 趋势 + 最近订单）/ 全站订单 / 退款审核 / 分析 / 审批 / 用户 |

三个实现细节：

1. **管理端页面全部懒加载**（`lazy(() => import(...))`）：客户永远不会打开这些表格，
   不该进客户的 bundle。构建产物印证：`AdminDashboard` 7.7KB / `OrderManager` 8.6KB /
   `RefundPanel` 5.9KB 各自成 chunk，客户主包没变大。
2. **工作台 → 具体页面的"带着筛选跳转"**：点"待发货 132"要直接落到订单管理**并且已经筛好**。
   实现用 `viewParams + navSeq`，`navSeq` 递增当 `key` —— 因为 React 里"已在订单页再点另一个筛选"
   时组件不会重新挂载，光传 props 是不生效的。
3. **趋势图不引图表库**：7 根柱子的 div 高度就是全部实现（ECharts 是 566KB 的懒加载 chunk，
   工作台是首屏，不能为它买单）。但**缺口日必须补齐**：后端只返回"有单的日期"，
   直接画会把 5 天画成 7 根柱子。

## 六、这一节踩的坑（都是"本地绿、换个环境红"那一类）

| 坑 | 现象 | 修法 |
|---|---|---|
| `ALTER` 写在 `CREATE` 前 | 开发库正常，空测试库 `relation "refunds" does not exist` | 新列进 CREATE，ALTER 放后面 |
| 计数查询漏 JOIN | 关键词加了 `u.display_name` 只改了列表查询 → `count(*)` 报 `missing FROM-clause entry for table u` | 计数查询带同一个 LEFT JOIN（用例里加"搜不到也要返回 0"） |
| `audit_log` 不参与 `reset_schema` | 断言"审计共 N 条"跨用例/跨运行累积，第二次跑就红（4 条对不上） | 按 `thread_id` 精确定位 + 断言**增量**，末行看内容 |
| 近 7 天变成 8 天 | `created_at >= now() - interval '7 days'` 含边界日 → 返回 8 个自然日 | `interval '6 days'` + 回归用例（第 7 天前的单不能进窗） |
| JSX `(` 里多个兄弟元素 | `{cond && ( <div/> <div/> )}` → esbuild `Expected ")" but found "className"` | 包一层 Fragment |
| 列表用 Fragment 简写 | `<>` 不能带 key → React "unique key" 警告，展开行复用错位 | `import { Fragment }` 用 `<Fragment key=...>` |
| 非 ASCII 查询参数 | 手拼 URL `?status=已付款` → `UnicodeEncodeError` | 一律 `urlencode(params)` |

## 七、退单联动（2026-09 第二轮）：订单状态 ↔ 退款工单

上线管理端之后暴露的下一个洞：**工单和订单互不相干**。售后 Agent 的 `create_refund`
只往 `refunds` 插一行，管理端审核只改工单自己的 `status` —— 实测：

```
19 张「已通过」的退款工单 → 对应订单还挂在 已发货/已收货，¥197,500 的退款查不到
11 张「待审核」的工单    → 订单没有任何"正在退款"的标记
分析模块"净成交额 = GMV − 已退款金额" → 库里根本没有"已退款"状态，无从可减
```

### 联动模型（三条规则）

```
建工单  → 订单「退款中」 + 工单记 order_status_before（退款前状态）
审核通过 → 订单「已退款」 + refunded_at（**退款前是待付款则「已取消」**：没付过钱的不叫退款）
审核驳回 → 订单退回 order_status_before（**该单还有别的待审工单时不退**：流程仍在进行）
```

### 四个关键取舍

1. **必须记 `order_status_before`**：驳回要"原样退回"，不记就只能猜 ——
   猜错方向是随机的（退回已付款？还是已发货？），而订单状态是业务事实。
   历史工单没这个字段时**不猜**：订单留在「退款中」并在审计里说明，交人工处理。
2. **「退款中」是闸门状态**：只能由退款审核离开（通过/驳回），不能再发货、不能再取消。
   留给管理端的口子只有"去审工单"——否则会出现"货也发了、款也退了"的双向损失。
   > 实现上有个顺序陷阱：`退款中 → 已退款` 本来就在合法边里（审核走的就是这条语义），
   > 所以"手工改状态"的判断**必须放在状态机校验之前**，否则同一个接口就能绕过工单
   > 把订单改成"已退款"——账上多一笔退款、系统里没有对应工单。
3. **工单插入与订单状态变更同一个事务**（`src/db.py::transaction()`）：
   拆成两个事务时，中途失败会留下"工单成了、订单没动"（老问题重演）或
   "订单进了退款中、却没有工单可审"（订单被永久冻结，因为它只能由工单离开）。
4. **状态机抽成 `src/order_flow.py`**：订单状态现在有**两条写入路径**（管理端 + 售后 Agent），
   状态机留在任何一条路径里，另一条就会绕过它。

### 口径落地（这一步才是"联动"的意义）

`src/analytics/schema_hints.py` 里把两个**一直混着用**的率拆开定义：

| 名词 | 算法 | 数据来源 |
|---|---|---|
| 退款率 | `status='已退款'` 订单数 / 订单数 | orders |
| 退款申请率（投诉口径） | **有退款工单**的订单数 / 订单数（含被驳回的申请） | refunds |
| GMV | `SUM(total) WHERE status <> '已取消'`（**含已退款/退款中**） | orders |
| 净成交额 | `SUM(total) WHERE status NOT IN ('已取消','已退款')` | orders |
| 退款中敞口 | `SUM(total) WHERE status='退款中'` | orders |

**这两个率真的不一样**（实测同一份数据）：已退款口径 Top3 = 0.10 / 0.083 / 0.064，
工单口径 Top3 = 0.225 / 0.170 / 0.167 —— 差 2.25 倍，第 2/3 名还是不同产品。

这件事是**评测用例逼出来的**：改完口径后 `refund_by_product` 用例开始失败
（模型按新语义层用"已退款"口径，而用例真值还是"工单"口径）。正确处理不是改断言让它过，
而是：① 问题里写清是哪个口径；② 真值改用同一口径；③ **另加一条用例**专门考工单口径，
逼模型分清两者。现在这两条用例成对存在（`refund_by_product` / `refund_requests_by_product`）。

### 不变量（自己踩过才写下来的）

> **有「待审核」工单的订单必须处于「退款中」**（终态订单例外：工单只是留痕）

手工回滚 E2E 误操作时我把订单退回原状态、却让工单留在"待审核"，
正好造出了这次要消灭的那种不一致。所以这条不变量被写进
`src/order_flow.py::check_refund_invariants()`，**回填脚本的 dry-run 和测试都用它自检**。

### 存量回填

`scripts/backfill_refund_linkage.py`（默认 dry-run，`--apply` 才动手；单事务 + 每笔写审计）：

```
① 待审核工单 → 订单进「退款中」：11 单，金额 ¥88,140
② 已通过工单 → 订单「已退款」（待付款则「已取消」）：19 单，金额 ¥197,500
③ 已驳回工单 → 只补记 order_status_before（订单不动）：8 张
合计 30 张订单状态变更，全部写审计
```

回填后口径自洽（可验证）：`GMV 7,256,860 − 已退款 197,500 = 净成交额 7,059,360` ✅
订单分布：已收货 182 / 已付款 132 / 待付款 121 / 已发货 113 / 已取消 24 / **已退款 19** / **退款中 11**。

## 七、还没做的（诚实清单）

- **订单状态机没有独立模块**：`ALLOWED_TRANSITIONS` 目前和读接口同处 `admin_orders.py`，
  真要长大会拆成领域模型 + 迁移表（每条转换的权限、必填备注、是否触发通知）。
- **退款通过 ≠ 钱真的出去了**：现在会改订单状态（已退款）+ 记 `refunded_at`，但**没有对接支付/账务**。
  真实系统还需要"审核通过 → 出账 → 回执 → 对账"的补偿链路（状态只是账务的影子，不能替代账务）。
- **没有批量操作**：132 条待发货只能逐条点（真实仓储场景会要"批量发货 + 导入运单号"）；
  退款审核同理，11 张工单只能一张张审。
- **没有导出**：管理员迟早要 Excel/CSV 导出，这条没做。
