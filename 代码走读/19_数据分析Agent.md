# 19 · 管理员数据分析 Agent（自然语言 → 只读 SQL → 结论 → 图表）

> 这一节讲一个**独立于客服链路**的第二套 Agent：管理员用一句话问业务数据，
> 系统自己规划、生成只读 SQL、校验、写结论、出图表。
> 代码位置：`src/analytics/`（语义层 / 只读层 / 分析图）、`app.py`（SSE 端点）、
> `web/src/components/AnalyticsPanel.jsx`（管理端界面）。

---

## 一、先建立心智模型：它和客服 Agent 是什么关系

| | 客服 Agent（03~12 步） | 数据分析 Agent（本步） |
|---|---|---|
| 输入 | 客户的一句话（中文） | **管理员**的一句话（中文） |
| 数据 | 商品目录、订单、对话历史 | **整个业务库**（订单/退款/产品/对话/审批…） |
| 危险动作 | 下单（写库）→ 靠 HITL 人工审批兜 | **执行 SQL** → 靠"只读四层防护"兜 |
| 输出 | 回复客户 | 结论 + 图表 + **可复核的 SQL** |
| 复用 | — | MCP 工具层、SSE 流式、节点事件、鉴权、限流、审计**全部复用** |

一句话：**客服 Agent 的难点是"别说错话"，分析 Agent 的难点是"别执行错 SQL"** ——
前者管住嘴，后者管住手。

## 二、动手之前先补数据地基（这一步最容易被跳过）

真实库里当时的状态（都是实测出来的，不是假设）：

| 问题 | 证据 | 处理 |
|---|---|---|
| 金额用 `REAL`（=float4） | `unit_price=14.2` 存进去变 `14.199999809265137` | 迁移成 `numeric(12,2)`，并用 `USING round(x::numeric,2)` 把噪声洗掉 |
| 3 行订单列错位 | `status` 存的是时间戳、`total` 是 `13800000000` | 由错位规律**确定性还原**（三行的 `quantity×unit_price` 与错位到 `shipped_at` 的金额精确吻合），原值快照写进 `audit_log` 可回滚 |
| 数据量太小 | 52 单 / 3 个月 → 图表只有一根柱子 | 造数脚本：600 单 / 8 个月 / 40 客户 / 退款 / 询价会话，且**注入可被发现的信号** |

**为什么必须造出"信号"**：如果造出来的数据没有规律，分析 Agent 就没有故事可讲，
演示时会变成"它算出了几个数"而不是"它发现了什么"。注入的三个信号：
① 3 个问题产品的退款率是全站 2.9 倍；② 3 个产品询价多却几乎不下单；③ 大客户集中（15% 客户贡献 64% GMV）。

> 造数脚本还有一个细节值得学：**脚本自己查库把注入信号打印出来**（而不是硬编码"我注入了 X"）。
> 初版我写死了"前 20% 客户贡献多数 GMV"，实测只有 27% —— 造数脚本吹牛比不造数更糟，
> 它会让人误以为数据里有信号。

## 三、只读四层防护（本模块的安全命门）

执行的是 **LLM 生成的 SQL**，属于不可信输入。参考实现只做了一层前缀白名单，
而 `WITH x AS (DELETE FROM orders RETURNING *) SELECT * FROM x` 的前缀正好是 `with` —— 能过校验、能删数据。

所以要四层（`src/analytics/sql.py`）：

| 层 | 手段 | 实测证据 |
|---|---|---|
| ① 账号 | 独立只读 PG 角色（`scripts/create_analytics_role.py`） | `CREATE/INSERT/UPDATE/DELETE/DROP` 全被**数据库**拒绝 |
| ② 连接 | `default_transaction_read_only=on` + `statement_timeout=15s` | 绕过语句层直接 UPDATE → `ReadOnlySqlTransaction` |
| ③ 语句 | 单语句、SELECT/WITH 开头、关键字黑名单、禁系统表与注释、**外层强制 LIMIT** | 8 条危险语句全被拒（含 CTE 里藏 DELETE、多语句、`pg_sleep`、注释绕过） |
| ④ 结果 | 行数上限 2000 + 单元格截断 + 截断标记 | 不写 LIMIT 的查询也被封顶，并提示"已截断" |

**两个实现细节**：
- 强制 LIMIT 要包 `limit+1` 行，多出来的那行专门用来判断"是否被截断"（包 `limit` 行永远看不出还有更多）；
- 只读层**拒绝 SQL 注释**（`--`、`/* */`），因为注释常被用来绕过关键字检查。
  副作用是"自己写的参考 SQL 也不能带注释"——这个策略对自己人也生效，是对的。

## 四、分析图：六个节点

```
planner ──► coder ──► executor ──► critic ──┬─(retry ≤2)─► coder
                                             ├─(还有步骤)─► coder
                                             └─(完成)─────► reporter ──► charter ──► END
```

| 节点 | 干什么 | 关键设计 |
|---|---|---|
| planner | 把问题拆成 ≤2 步可执行步骤 | 步数上限是**延迟主因**（每步≈2 次 LLM 调用，单次 10-30s） |
| coder | 生成一条只读 SQL | 要求紧凑输出（输出越短越快） |
| executor | 走只读层执行 | 失败**不抛异常**，把错误当结果返回给 critic |
| critic | 判断结果能不能采信 | 程序兜底：执行失败**无条件** retry，不把判断权全交给模型 |
| reporter | 写结论 + 给图表意图 | 一次产出两样（省一次 LLM 调用） |
| charter | **纯程序节点** | 把意图 + 真实数据拼成可渲染 spec |

### 表关系从哪来（2026-09 的演进，值得单独讲）

参考实现靠 `get_foreign_keys_text()` **运行时读外键**自动生成 JOIN 依据；
而本项目当时**一个外键都没有**，所以第一版只能**手写** `RELATIONS`。手写的代价是谁都能想到的：
新增表忘了登记、关系写错没人发现（而且没有测试守着）。

后来补上了：① 立起"凡是被接受的身份，users 里必须有行"（`ensure_user_row` 影子账号）——
因为实测有 63 个 user_id 在业务数据里出现却没有账号行；② 清掉 313 行历史孤儿；
③ 加 7 条外键（`NOT VALID → VALIDATE` 两步）；④ 于是关系改成
**运行时读外键**，手写部分只剩"外键表达不了的语义"（如 `audit_log.actor` 是自由文本）。

```python
# src/analytics/schema_hints.py
async def load_fk_text() -> str:      # 从 pg_constraint 读外键 → 拼成 JOIN 依据
def semantic_hints(fk_text="") -> str:  # 有外键用它，没有就退回手写兜底
```

**一句话总结**：能靠数据库约束表达的，就别手写进 prompt —— 手写的东西越多，
越容易和真实结构漂移。

### 三个与参考实现不同的关键点

**① 图表数据不经过 LLM。** 模型只输出"用哪条结果 + 图型 + 哪列做 x + 哪列做值"，
数值由程序从查询结果里取：

```python
# src/analytics/graph.py::_build_chart
item = {"x": row[xi]}
for s in series:
    item[s] = float(row[columns.index(s)])   # ← 来自真实结果，模型编不了
```

参考实现让模型输出图表内容，一旦模型编数，**柱子高度就是假的**——而图恰恰最容易被相信。

**② 结论里的数字做程序校验。** reporter 写完结论后逐个数字回查结果集，
查不到的写进「数据局限声明」。三个必须处理的细节：
- 数字要带**量级单位**解析（"838.6 万"→8,386,000），否则"1 个亿"里的 `1` 会被"小整数豁免"放过；
- 日期/时间窗口/编号（`2026-07`、`最近 90 天`、`P0163`）**不算指标**，否则误报一堆，管理员就不看告警了；
- **记录元数据也要算出处**（"结果共 221 行"里的 221 是工具给的真实 row_count，漏掉会误报）。

**③ 容差要按量级决定。** 统一给 ±0.51 的绝对容差会让 0.009 和 0.1667 判成"同一个数"
（比率是 0~1 的小数），编造的比率就能蒙混过关。

## 五、评测：Text-to-SQL 没有评测就是玩具

`src/analytics/eval_cases.py` + `scripts/eval_analytics.py`：7 条用例，**期望值由参考 SQL 现算**。
好处是数据一变（重跑造数脚本）期望值自动跟着变，不会被"我猜的数"污染。

拦三类回归：
1. **口径退化**（又按"退款笔数"而不是"退款率"回答）；
2. **数据质量回退**（错位金额 `13800000000` 再次出现在结论里）；
3. **只读被绕过**（诱导"删掉已取消订单"必须被拒且数据库不变）。

判定用的是**确定性检查**（提到没提到、数值命中没命中、数据库变了没有），
不是让 LLM 给自己打分——LLM 评审会给出"看起来合理"的分数，但**发现不了口径错误**。

## 六、踩过的坑（都很典型）

| 坑 | 表现 | 教训 |
|---|---|---|
| 同一问题两个数字 | 问"退款率最高的颜色"，一次 9.8%、一次 4.4%——planner 自己加了"近 90 天" | 让模型自己决定口径 = 数字不可复现。语义层必须写死"默认不加时间过滤" |
| LangGraph 丢弃未声明的 key | 忘了往 TypedDict 加 `chart_intents` → 图表全空且**不报错** | 新增 state 字段必须同步改 TypedDict |
| 盲替换两次翻车 | ① 替换没生效却打印"已优化" ② 多行文本注进单行字符串 → SyntaxError | 替换后**立刻 `py_compile` + 断言生效** |
| ECharts 让主包 +570KB | 构建告警 chunk > 500KB | `React.lazy` 懒加载 + 按需注册图表类型 |
| 参考 SQL 自己写错分母 | `JOIN refunds` 让分母只数被退款的订单 → 结果集为空 | 算比率一律 `LEFT JOIN`；**评测的"标准答案"也要被验证** |
| 安全判定盯措辞 | "回答里必须出现 只读/无法" → 把实质正确的回答判成失败 | 判定盯**行为**（数据变了没、有没有谎称删除），不盯措辞 |

## 七、Q&A

**Q1：为什么不用现成的 text-to-SQL 框架？**
框架解决的是"生成 SQL"，本项目真正的难点在它之外：① 库**没有外键**，JOIN 依据只能手写语义层；
② 数据本身有质量问题（错位行、float 金额），要先治理；③ 安全要四层，因为 SQL 是不可信输入；
④ 结论要防编造。这些都得自己写，框架帮不上。

**Q2：LLM 生成的 SQL 会不会把库读挂？**
三层挡着：`statement_timeout=15s`（防慢查询）、外层强制 `LIMIT`（防大结果）、
只读角色（防写）。另外连接池只给分析层 2 个连接，不会抢占业务连接。

**Q3：模型答错了怎么办？**
分三类处理：① SQL 报错/查不出 → critic 带反馈让它重写（≤2 次）；② 重试用尽 → **如实降级**，
把"这一步没查成"写进结论的局限声明，不死循环、不静默；③ 数字没出处 → 进局限声明。
**"自信地胡说"是这类 Agent 最危险的失败模式**，所以宁可少写，不可编造。

**Q4：怎么保证同一问题每次答案一致？**
口径写在语义层（GMV 排除已取消、退款率分母是订单数、默认不加时间过滤、小样本不参与排名），
并且有评测用例盯着——如果某天模型又开始自行加时间过滤，评测会红。

**Q5：一次分析要多久？为什么？**
快速模式约 30 秒（1 步），标准模式约 2 分钟（2 步）。瓶颈是 LLM 的**输出长度**
（实测约 30 字符/秒，生成一条 600 字符的 SQL 就要 20 秒）。优化手段：限制步数、
把"图表选型"从 LLM 改成纯程序、要求紧凑 SQL、把 critic 的输出压到 40 字。
全程 SSE 流式，每一步都即时可见，所以等待是可解释的。

**Q6：这套东西在生产还差什么？**
① 多轮追问（现在一问一答）；② 结果缓存（同一问题重复问很浪费）；
③ 定时报告（每天自动跑一次固定问题集，推送给管理员）；
④ token 成本核算（每次分析的 LLM 花费要可见）；⑤ 分析结果导出（Excel/CSV）。
